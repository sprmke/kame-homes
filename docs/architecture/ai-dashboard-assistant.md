## 1. What it is

A chat assistant embedded in the admin dashboard (floating launcher, bottom-right, hidden for super-admins) that answers operational questions and executes actions — strictly scoped to the signed-in user's real RBAC permissions, never more. Two-layer kill switch (platform-wide off by default, org opt-in, optional per-property disable). **Plan gating:** property routes require **`aiDashboardAssistant`** on the property subscription (`useAiAssistantAccess` on the client; `dashboard-assistant-chat` gates proposing a message/action, `dashboard-assistant-confirm` re-checks before executing a previously-queued Tier-2 action — closes the window where a property downgrades between proposal and confirmation). UI when blocked by plan only (not the kill switch): the panel, history, suggestion chips, and composer all render normally (preview-open) — sending a message, picking a suggested question/action, or submitting the composer opens the upgrade modal instead of calling the chat API. **Parking routes:** when `pageContext.parkingId` is set and no `propertyId`, the plan check gates on the org directly — `requireOrgFeature(organizationId, 'aiDashboardAssistant')` (`_shared/planEntitlements.ts`), property-independent (resolves via `resolveOrgEntitlements`, no property proxy). `dashboard-assistant-confirm`'s Tier-2 re-check mirrors this for org/parking-scoped conversations too. Closed 2026-09-09 — previously this path was unconditionally ungated (`PARKING_INTERIM_UNGATED_FEATURES`); see [`parking-property-parity.md`](../workflow/in-progress/parking-property-parity.md). Gemini 2.5 Flash via `_shared/geminiToolCallClient.ts`, tool-calling loop capped at `MAX_TOOL_ROUNDS = 4` rounds per turn.

### Context model

Two separate signals are sent on every chat turn:

| Signal                                                 | Meaning                                                                                                                        | Source                                                                                                          |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `pageContext: { propertyId?, parkingId?, bookingId? }` | Ambient route — the page the host is looking at. Load-bearing for kill-switch property disable and for cross-scope escalation. | Current React Router params (`propertySlug` / `parkingSlug` / `bookingId`). Never overwritten by composer pins. |
| `attachedContext: AttachedContextItem[]`               | Explicit pins the host added in the composer (booking, property, finance item, …). Max 8.                                      | Composer chips. Validated per-type (id format + RBAC) in `dashboard-assistant-chat`.                            |

Tool argument resolution is **explicit args → attached context → ambient `pageContext`**. The system prompt lists every attached item grouped by type. Cross-scope escalation treats attached ids (and each item's `propertyId`) as in-scope, so pinning a booking on a different property page does not itself force Tier 2 when the model acts on that pin. Confirm-time re-check restores the same scope from `__assistantScope` stored on the pending action.

Types: frontend `ui/src/features/dashboard/ai-assistant/lib/attachedContext.ts`; backend `_shared/dashboardAssistantAttachedContext.ts`.

**Contextual starter prompts:** once the host pins one or more context items, the empty-chat **Questions / Actions** starter cluster swaps the generic random pool for ranked, module-specific prompts (`lib/moduleSuggestions.ts`). Each `AttachedContextType` (booking, property, parking booking, finance item, maintenance item, pricing date, …) has its own **Questions** and **Actions** lists, ranked most → least common against the real tool catalog. Pinning more than one module type merges their ranked lists fairly by rank tier (each pinned module's rank-1 prompt is offered before any pinned module's rank-2 prompt), in canonical module order (`ATTACHED_CONTEXT_TYPES`). With no context pinned, the starter cluster falls back to `assistantSuggestions.ts`'s random pool, unchanged.

**Mid-conversation pill suggestions:** each pinned context chip in the composer is also a button (text shifts to the primary teal on hover or while open) that opens a compact popover showing that single module's ranked Questions / Actions. Tapping a prompt sends it as a chat message carrying the currently pinned context. This works during an existing conversation, not just the empty state — the host can drill into one pinned module at a time without retyping. The X button beside each pill still removes the pin.

The composer uses a **two-tier picker**:

1. **Module quick-picker** — route-aware bookmark icon left of paperclip (`lib/contextPickerRegistry.ts`). Offers the current page's entity type (bookings, properties, team, finance, maintenance, parking bookings, inbox, marketing templates, pricing dates, notification modules, public pages, or tickets). Pins persist across pages.
2. **Attachments** — paperclip popover (Photo / File) beside the context hub.
3. **Speech-to-text** — microphone icon (third toolbar control, when the browser supports the Web Speech API on HTTPS). Tap to start/stop; interim words fill the composer; existing text is kept as a prefix. Chrome, Safari, and Edge; requires microphone permission.
4. **Command palette** — **Search all modules…** in the context hub footer, or **Cmd/Ctrl+K** while the chat composer is open. Both use a **two-step drill-down**: module list first, then items within the chosen module (**Back** returns to modules). Centered `cmdk` dialog (`ChatContextCommandPalette.tsx`) shares the same catalog hooks as the bookmark popover (`ChatComposerContextHub.tsx`). Pins still travel as `attachedContext[]`.

**Canvas overlay** (`ChatCanvasOverlay.tsx`): canvas-worthy blocks (any `stepper`, `data_table` with more than 8 rows) render inline as a compact card with **Open**. At `lg` (1024px+) the sheet widens and the canvas sits beside a 24rem chat column. Below `lg` (375/768) the canvas replaces the chat; **Back** returns to the thread. The command palette stays a centered dialog — it is not moved into the canvas.

### Turn progress (SSE)

When the client sends `Accept: text/event-stream` or `stream: true`, `dashboard-assistant-chat` emits live events from `_shared/dashboardAssistantStreamEvents.ts`:

| Event                       | When                                                                                                                                                     |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `turn_started`              | Immediately after the user message is persisted — carries `conversationId` so the client can recover if the stream is cut mid-flight                     |
| `phase`                     | understanding → executing → synthesizing → safety                                                                                                        |
| `tool_start` / `tool_done`  | Each tool in the Gemini loop (with human labels from `assistantToolLabels.ts`)                                                                           |
| `plan` / `plan_update`      | Multi-tool batches (2+ tools in one round; steps accumulate across rounds)                                                                               |
| `text_start` / `text_chunk` | After synthesis — chunks the first `text` block (~18ms apart) before the terminal `blocks` event                                                         |
| `blocks` / `error`          | Terminal success or failure (`error.aborted: true` when the host cancelled; optional `appliedEffects` when Tier-1 writes partially applied before abort) |

**Cancel:** composer Stop aborts the fetch; the stream `cancel` callback aborts the server turn. Tier-1 auto writes are **queued during the tool loop** and only **committed after synthesis + safety** — Stop before commit leaves the app unchanged (queued writes discarded; uncommitted user message deleted). If Stop arrives mid-commit, already-applied Tier-1 writes are audited and disclosed via `error.appliedEffects`; the user message is kept. The client reloads the conversation (when an id exists) so the thread matches the database.

**Interrupted streams:** if the SSE connection dies mid-turn (browser `ERR_INCOMPLETE_CHUNKED_ENCODING`, local `functions serve` hot-reload, proxy cut), the client maps that to a clear “Connection interrupted” error and **auto-retries once** via `regenerate: true` when a `conversationId` is known — so a transient cut does not leave a raw “network error”.

**Regenerate:** `regenerate: true` + `conversationId` deletes assistant messages after the last user row, expires pending Tier-2 proposals for that user message, and re-runs without inserting a duplicate user message. Not available for attachment turns.

UI: `AssistantTurnProgress` during tool phases (**present-tense** step labels — e.g. “Understanding your question”, “Preparing your answer”); streaming text preview replaces the progress panel once `text_chunk` events arrive. Completed turns render as a single **`AssistantMessageCard`**: optional collapsed **Steps** header → answer blocks (text, stepper, confirmations, tables, …) → **Suggestions** footer. `partitionAssistantBlocks` strips `activity_timeline` / `task_plan` / `quick_actions` from the flat block list for layout; `task_plan` is omitted when `activity_timeline` is present. **`dashboardAssistantHostDisplay.ts`** builds a host-label index from tool results + composer pins and rewrites quick-action chips, text, and ID columns before persistence (bookings / parking stays → `guestName · check-in–check-out · status`; inbox → participant + platform; maintenance / team / marketing / parkings → `hostLabel` from list tools). List/read tools emit a `hostLabel` field the model should copy. System prompt accuracy rules apply to **all modules** (bookings, inbox, maintenance, team, parking, marketing, finance): never deny an entity that appeared in this conversation or tool results; explain blockers and next valid steps instead. After the host selects an entity, suggestions are next useful actions — never a re-pick of the same `hostLabel` chip (`filterEchoSuggestionChips`). Panel header shows today's message count vs org daily limit (`includeUsage=true` on settings fetch).

**Conversation memory (same thread):** each `dashboard-assistant-chat` turn loads recent prior messages via `_shared/dashboardAssistantConversationContext.ts` (excludes the current user row). A short deterministic summary is appended to the system prompt (`Conversation so far`), and the same turns are seeded into Gemini `history` before the current user message so follow-ups (“that guest”, “the thread”, “same as before”) stay continuous without a separate summarizer model call. The summary extractor now includes `flow`, `diagram`, and `map` blocks in addition to text/table/stepper/action blocks so structured turns stay represented across follow-up prompts.

## 2. Safety model (applies to every tool, no exceptions)

1. **Independent RBAC re-check.** Every tool re-derives the permission it needs and re-runs the real RBAC primitive (`verifyPropertyAccess` / `verifyOrgAccess` / `verifyOrgOwner` / `verifyPropertyOwner` / `verifyOrgTeamAccess` / `requireTeamPropertyAccess`) against the **original request's JWT** — never anything the model asserts. A tool call with a forged/wrong `propertyId` in its arguments fails the RBAC check the same way a direct API call would.
2. **Three-tier risk model**, computed server-side, never by the model:
   - **Tier 0 (read)** — always allowed if the RBAC check passes. Never touches the database.
   - **Tier 1 (auto-executed)** — runs at **end-of-turn commit** (after synthesis + safety), surfaced to the host as a visible "done automatically" card. Reserved for idempotent or clearly-reversible writes. Cancel before commit discards the queue with no DB writes.
   - **Tier 2 (confirm-required)** — the tool call returns a `proposed` result; nothing is written yet. A separate `dashboard-assistant-confirm` call (triggered by the host clicking Confirm in the chat UI) is the only path that actually executes it. A pending proposal expires after 15 minutes.
3. **Escalation rules that override a tool's normal tier** (`classifyActionRisk` in `dashboardAssistantRiskClassifier.ts`):
   - **Bulk escalation**: if the model requests 2+ write tools in one turn, every one of them is forced to Tier 2, regardless of what each would individually resolve to. Also: any tool round with **2+ tools where at least one is a write** forces Tier 2 for all writes in that round (read + write mix).
   - **Cross-scope escalation**: if a tool's target booking/property is outside both `pageContext` and `attachedContext` (composer pins), it's forced to Tier 2.
   - `propose_transition_booking` specifically has **no fixed tier** — it's computed per-call from the real booking-status graph (`statusMachine.ts#canTransition`): a plain forward, non-financial, non-override edge is Tier 1; anything that's a manual-override edge, a cancellation, an SD-refund finalization, or carries a financial payload field is Tier 2.
4. **Immediately-before-execution re-check** (`assertActionSafeToExecute`). Even a Tier 1 tool re-derives its tier from current DB state right before writing — a booking's status may have changed between proposal and execution; the guard hard-throws if the recomputed tier disagrees with what was expected. This runs for Tier 0/1 auto-execution and for Tier 2 confirm-execution alike.
5. **Post-generation grounding check** (`assertBlocksGrounded` in `dashboardAssistantSafetyGuard.ts`) — every response block is checked against the actual tool-result data before being sent to the host; ungrounded blocks are dropped, not shown. Empty `stat_list` / `data_table` / `link_list` / `file_list` cards are stripped (`sanitizeAssistantChatBlocks`); if the model still omitted `pendingTasks`, `bookedStays`, or a requested booking file that a tool actually returned, `hydrateAssistantBlocksFromTools` fills them in. A `plan_booking_journey` result becomes a `stepper` (never model-authored). After Tier-1 auto or Tier-2 proposed `action_confirmation` blocks are assembled, `nestBookingJourneyStepper` runs a final pass so the first `propose_transition_booking` confirm nests on the stepper's **current** step instead of rendering standalone (including Tier-2 short-circuit turns that skip structured synthesis). Status codes in text (`READY_FOR_CHECKOUT`) are rewritten to human labels. `file_list` and `image` URLs must match a tool-returned storage URL (never a model-invented link); `map` blocks require a grounded `href`, and any provided `lat`/`lng` must either appear in grounded facts or match coordinates encoded in that grounded URL. The UI signs private buckets at preview time via `get-booking-asset-url`.
6. **Full audit trail** — every executed write (Tier 1 auto or Tier 2 confirmed) is recorded and surfaced on the relevant booking/property's "Actions taken by AI assistant" card.
7. **External-facing actions are a stricter, separate risk category** (scaffolded in Phase 2, now used by `propose_send_inbox_reply` and `propose_publish_to_meta` — see §3.7). Sending a real message to a guest or publishing to a public social account is categorically riskier than any internal DB write, always Tier 2, with its own distinct destructive-styled confirm UI.
8. **A "never build" list exists at the tool-catalog level, not just as a prompt instruction** — irreversible/maximal-blast-radius actions are simply never registered as callable tools (see §6). No amount of prompting can make the model call a tool that doesn't exist.

### 3.5 Pricing (Phase 6) — property + parking

### 3.7 External-facing actions — the stricter risk category, now in real use (Phase 2 scaffold → populated)

`_shared/dashboardAssistantRiskClassifier.ts` exports `EXTERNAL_SEND_TOOL_NAMES` — containing `propose_send_inbox_reply`, `propose_publish_to_meta`, and `propose_send_workflow_email`. `isExternalSendTool()` gates two things end-to-end:

1. **Classification**: any tool in this set is always Tier 2, registered directly in `TIER2_ONLY_TOOL_NAMES` too — never left to fall through the generic default-tier logic.
2. **Confirm UI**: `dashboard-assistant-chat/index.ts` sets `isExternalSend: true` on the `action_confirmation` block for these tools; `ActionConfirmationBlock.tsx` renders a destructive-tinted card, an explicit "sends/publishes for real, right now — can't be undone" warning line, and a "Send" button (destructive variant) instead of the generic "Confirm" — visually and textually distinct from every other Tier-2 confirmation in the app, so a host can't mistake it for an internal-only, easily-undone action.

| ------------------------ | ---- | ---- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

`get_property_analytics` calls the same `_shared/analyticsService.ts#computeAnalyticsBundle` and `_shared/hostPlaybook.ts#matchPlaybookArticles` the Analytics page itself uses — one implementation, no parallel copy that could drift. Kept in its own file, `_shared/dashboardAssistantAnalyticsTools.ts`, mirroring the `dashboardAssistantOpsTools.ts` (Channel sync) convention — wired into the main dispatcher additively (import + 2 switch cases + 2 declaration-list entries), not by growing the dispatcher's own logic. The page's **Ask about these numbers** button (`PropertyAnalyticsPage.tsx`) simply calls the existing zero-argument `openAiAssistant()` — no context-pinning change was needed since `pageContext.propertyId` already flows from the route the same way it does for every other module's launcher.

**Analytics answers, like Finance (§4), must put figures in a `stat_list`, never in the `text` block** — live-verified during the module's build: `guardDashboardAssistantResponse` (the free-text safety reviewer) only ever sees `groundingPrompt`, which bakes in **this-calendar-month** finance/maintenance totals but has no way to carry analytics figures (Analytics is date-range selectable, not a fixed period), so any exact number the model puts straight into prose gets flagged as an apparent hallucination and the whole response is dropped. The system prompt's Analytics line requires a qualitative `text` block (state/headline, no numbers) plus a `stat_list` built from the tool's own `*Pct`/`*Display` fields — `stat_list` values are checked by the separate, reliable `assertBlocksGrounded` structural check instead, which does see the real tool results.

**Not built / explicitly excluded**: `analytics-ai-review` **POST** (Regenerate) as a chat tool — a narrow write (creates an advisory review row, never mutates a rate/setting) but still excluded for now; hosts use the **Regenerate** button on the Analytics page (rate-limited 1/hour/property, same limit a chat tool would need to respect anyway). Org-level portfolio analytics (`/org/:orgSlug/analytics`) has no assistant tool yet — property-scoped only, matching where `pageContext.propertyId` is actually set.

## 4. Architecture-level facts every tool call relies on

- **Grounding prompt** (`dashboardAssistantContext.ts#hostSafeGroundingFactsToPrompt`) injects, every turn: today's date + Asia/Manila timezone, the requesting host's name, org name/slug, the accessible property list (filtered to `pageContext.propertyId` when set), a 4-status booking-count summary, the resolved `permissions[]` array, and finance/maintenance **this calendar month** totals using the same Net Profit math as the Finance page (only if the host has `finance:view`/`maintenance:view` and ≤5 properties in scope).
- **Finance answers**: system prompt requires a short text explanation (property + date range + plain-language breakdown) plus a `stat_list` of Total Income / Total Expenses / Net Profit from `get_finance_summary.display` — never a lone "Grand Net" figure. `grandNet` (completed-stay host net + operating net) is an export/internal metric and is not returned by the chat tool.
- **Property scope**: when `pageContext.propertyId` is set (host is on a property route), tools resolve that property by default and grounding finance is property-scoped; org-wide answers only when the host is outside a property route or explicitly asks across properties.
- **Tool-call loop**: up to 4 rounds; Gemini can request multiple tool calls in one round, and results feed back for further reasoning. On round exhaustion, the assistant still attempts to synthesize a real answer from whatever was gathered (not just a canned "ask again" message) via a final structured-output call over the accumulated tool-call history.
- **Knowledge base**: `search_knowledge_base` reads `ai_dashboard_assistant_knowledge_base`, populated by `bun run sync:ai-knowledge-base` (local) / `:dev` (hosted dev) from the "Host-facing knowledge" Q&A sections in `docs/guides/routes/**/*.md`. **This has no automatic trigger** — re-run it by hand whenever a route guide's knowledge section changes, or the tool silently returns stale/empty results.
- **Attachments**: hosts can attach images/PDFs to a chat turn (paperclip in composer); stored via `_shared/dashboardAssistantAttachments.ts`, passed to Gemini as multimodal parts **and** available to `propose_apply_booking_attachment` by `attachmentPath` (same conversation, including later turns via conversation summary). Apply uses `_shared/bookingAssetUpload.ts` (same path as `upload-booking-asset`). Paths are allowlisted under `{orgId}/{userId}/{conversationId}/`; `resolveAssistantAttachmentPath` also accepts a bare filename or accidental `ai-assistant-attachments/` prefix and maps it to the matching file in that folder. Overwrite always Tier-2 warn+confirm. Vision for “what is this file?” is still strongest on the turn the file was attached.
- **Booking files in replies**: `get_booking` / `get_booking_documents` return the same Files-tab storage URLs (approved GAF, pet forms, receipts, IDs, parking). Chat renders them as `file_list` cards; invented URLs are dropped. Private buckets (`approved-gafs`, `approved-pet-forms`, `sd-refund-receipts`) are signed in the UI via `get-booking-asset-url`, same as booking detail.
- **Workflow emails from chat**: `propose_send_workflow_email` covers every Automation Triggers kind (external_send confirm UI).
- **Conversation history**: `dashboard-assistant-conversations` (GET, list + single) backs the panel's History view; conversations are private per user, capped at the 20 most recent (no pagination yet). Within an open thread, `dashboard-assistant-chat` also injects prior-turn summary + Gemini history via `dashboardAssistantConversationContext.ts` so new messages keep continuity.

## 6. Out of scope — nothing meaningful to expose (verified, not assumed)
