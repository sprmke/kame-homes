## 4. Routing and pages (current behavior)

Defined in `ui/src/features/guest/marketing/routes/index.tsx`, `ui/src/features/guest/property/routes/index.tsx` (operational guest flows under `/properties/:propertySlug/...`), and `ui/src/features/dashboard/**` (admin + tenancy). All are merged in `ui/src/routes/index.tsx`.

**Per-route operator guides:** **`docs/guides/routes/`** mirrors these URLs (index: **[[guides/routes/README|Route-based operator guides]]**). Update the matching guide when changing page behavior, save flows, or validation (see **`.cursor/rules/route-guides.mdc`**).

**Multi-tenancy (Phase 1):** Admin routes are nested under **`/org/:orgSlug/property/:propertySlug/...`** and **`/org/:orgSlug/parking/:parkingSlug/...`**. Each **organization** has exactly one **owner** (`organizations.owner_id` → `auth.users.id`); a user may **own at most one** org, and may be assigned to additional orgs as an invited **org admin** (`organization_members`) or **property member** (`property_members`). **`/org`** is a redirect hub (no picker): last-used org dashboard, else first org, else **`/onboarding`**. **`organizations.host_modes`** (`property` \| `parking`) and org-level **`/parkings`** list support parking inventory as a peer to properties. **Property-only members** have no org-scoped permissions (`ORG_PROPERTY_MEMBER_PERMISSIONS` is empty); org routes redirect to their assigned property and the sidebar org name is read-only. Parking v1: org owner + **`org:parkings:*`** only (no `parking_members`). Legacy flat paths redirect to the last-used or first org/property/parking. New users with no org land on **`/onboarding`** (host type: property, parking, both, or add later). Property-scoped admin edge functions use **`verifyPropertyAccess`**; parking-scoped use **`resolveScopedParkingAccess`**. **`list-organizations`** returns owned orgs plus orgs where the user is an org admin or has active property membership (each row includes **`accessKind`**); **`list-properties`** / **`list-parkings`** return org assets for owners/org admins.

**Property settings UI:** **`/org/:orgSlug/property/:propertySlug/settings`** — `PropertySettingsCard` (`AdminSectionNavLayout`): **Basic information**, **Photos & Videos** (drag-reorder gallery, primary image, upload/delete via **`upload-property-media`** → Storage bucket **`property-media`** + **`properties.settings.media`**; max **9 images** / **1 video**, 5 MB images / 25 MB video), **Property details**, **Amenities**, **Location & Access** (Google Places search + interactive map pin; persists **`properties.address`** plus **`properties.settings`** `latitude`, `longitude`, `mapsUrl`, `placeId`, and parsed city/province/country/zip), **Payment**, **Building Forms**, **Integrations** (per-property **AI services** test, Telegram configure links), **Danger zone** (archive → `INACTIVE`; delete via **`delete-property`** when no bookings). **Saves today:** profile DB columns via **`update-property`** + **`properties.settings`** JSONB merge + operational fields via **`app-settings`**. Property **name** is unique per organization (case-insensitive; migration **`20260703160000_properties_org_name_unique.sql`**). Condominium tower options are driven by selected residence (`propertyResidences.ts`). Operator guide: **[[guides/routes/org/property/settings|Property Settings — operator guide]]** (index: **[[guides/routes/README|Route-based operator guides]]**).

**Team (shipped):** Property team at **`/org/:orgSlug/property/:propertySlug/team`** — **`property-team-*`** + **`usePropertyTeam`** ([property team guide](../guides/routes/org/property/team.md)). Org team at **`/org/:orgSlug/team`** — **`org-team-*`** + **`useOrgTeam`** ([org team guide](../guides/routes/org/team.md)). Roles: property **Manager / Staff / Viewer** (+ custom); org **Owner** (virtual) + **Admin**. Invite emails + **`/accept-invite`** (property or `scope=org`).

**Activity (shipped):** Read-only org activity / audit timeline at **`/org/:orgSlug/activity`** (guard **`org.dashboard:view`**), **`/org/:orgSlug/property/:propertySlug/activity`** and **`/org/:orgSlug/parking/:parkingSlug/activity`** (guard **`bookings:view`**) — `ui/src/features/dashboard/activity/` + `useActivityLog` → **`list-activity-log`**. Sidebar entry per scope. Reusable `<EntityActivityHistory>` panel on the booking detail page. Guides: [org/activity.md](../guides/routes/org/activity.md), [org/property/activity.md](../guides/routes/org/property/activity.md), [org/parking/activity.md](../guides/routes/org/parking/activity.md). Full plan + emitter ledger: `docs/workflow/in-progress/org-activity-audit-log.md`.

**Staff access:** **Org owner**, **org ADMIN**, and **platform admin** retain implicit full property access; **active `property_members`** rows grant scoped permissions via JSONB.

**Property scoping (Phase 1c–1d):** Admin list/dashboard/finance/maintenance/**property settings** endpoints accept **`?property_id=<uuid>`** (UI sends it from route context via `usePropertyIdParam` / `scopedFunctionsUrl`). **Org settings** (`org-settings`, `upload-org-settings-asset`) accept **`?org_id=`** or **`?org_slug=`** (`scopedOrgFunctionsUrl`). Server resolves with `resolveAdminPropertyId` / `resolveAdminOrgId` — validates ownership when explicit, otherwise first owned property/org. Booking-scoped admin actions verify the booking row belongs to the resolved property. **`upload-app-settings-asset`** persists per-property assets. **`upload-org-settings-asset`** persists team logo per org. Public **`get-booked-dates`** and **`submit-form`** accept **`?property=<slug>`** or **`?property_id=`** (`resolvePublicPropertyId`; defaults to Monaco 2604 when omitted). Guest calendar/form forward **`?property=`** from the URL when present. Org **Properties** page and **`guestPublicPaths.ts`** build shareable calendar links as **`/calendar?property=<slug>`** (legacy **`/?property=`** redirects from the marketing landing).

**Phase 1e (shipped):** Scheduled jobs are property-aware. **GAF/pet approvals** use Resend inbound **`approval-email-webhook`** (per-property plus-address). Legacy note: migration **`20260629220000_gmail_listener_state_per_property.sql`** / table dropped in **`20261010120000_drop_gmail_listener_state.sql`**. **`sd-refund-cron`** resolves **`app_settings` per booking**. All five **telegram crons** iterate **`properties`** and scope settings, bookings, or line items by **`property_id`**. Event-driven Telegram notifies (submit, cancel, admin uploads) load settings for the booking’s property. New booking asset uploads use **`{propertyId}/{bookingId}/{fileName}`** via **`bookingStoragePaths.ts`** (legacy URLs without the prefix still work).

**Phase 1f (shipped):** Per-property integration credentials (pattern aligned with **kame-ops** `integrations` table). Migration **`20260629160000_property_scoped_integration_credentials.sql`**: drops singleton `id = 1` CHECK on settings tables; adds **`bot_token_encrypted`** / **`chat_id_encrypted`** on each **`telegram_*_settings`** row (AES-256-GCM via **`GMAIL_OAUTH_TOKEN_ENCRYPTION_KEY`**); Runtime resolution is **DB-only** for operator settings: **`propertyTelegramCredentials.ts`**, **`appSettings.ts`**, **`propertyIntegrationStatus.ts`**, and **`emailService.ts`** (all workflow + notify emails resolve `app_settings` from `booking.property_id`). **`create-property`** calls **`seedPropertySettings`**. Marketing/staff scheduled sends match each property’s Manila schedule inside a shared **5-min pg_cron** dispatcher (`ensure_telegram_multi_property_cron_dispatch`). Admin UI: all five Telegram settings pages expose bot token + chat id; Settings → Integrations shows **`propertyIntegrations`** (Property / Missing) + **`platformSecrets`** (shared Edge env only).

**Phase 2g (removed):** Retired **Connect Google** OAuth (Gmail listener, Calendar, Sheets). Production GAF/pet approvals use Resend inbound **`approval-email-webhook`** only; hosts do not connect Google accounts.

**Org dashboard (shipped):** **`/org/:orgSlug/dashboard`** — org-wide KPIs (properties + parking when present), revenue/bookings area chart (working toggle), large booking-status donut (period-scoped; total in center), recent bookings, pending actions, and listings performance. Equal-width board layout aligned with the property dashboard. **`BookingDateRangeFilter`** in the header. Data from **`dashboard-stats?org_slug=…&from=&to=`**.

**Phase 2 — optional hardening (backlog):** Postgres RLS tightening on bookings/settings (admin scoping today is edge-function + ownership checks); drop Monaco default when **`property`** cannot be resolved on public guest APIs.

**Mark nested docs complete (admin):** on **`PENDING_DOCUMENTS` → `PENDING_DOCUMENTS`**, payload **`document_completion_target`** takes a **requirement id** (`gaf`, `custom-2`, …) or a legacy `PENDING_GAF` / `PENDING_PET_REQUEST` literal; **`PENDING_PARKING_REQUEST`** writes **`parking_completed_at`**. Everything else is written into the **`document_requirement_completions`** JSONB map under the resolved requirement id (`gaf`/`pet` also dual-write their named columns), so a renamed requirement completes correctly instead of returning success with no write; an id the property has no requirement for is **rejected with an error**. **Manual back from ready-for-check-in:** admins may move **`READY_FOR_CHECKIN` → `PENDING_DOCUMENTS`** (same as the simplified pipeline “Back to Pending Documents” step) to reopen the nested docs workflow without going through legacy `PENDING_PET_REQUEST` / `PENDING_PARKING_REQUEST` / `PENDING_GAF` only; deeper recovery edges remain on `statusMachine.ts#MANUAL_OVERRIDE_GRAPH`.

**Ready-for-check-in email:** `WorkflowOrchestrator` sends it when moving **forward** to `READY_FOR_CHECKIN` from **`PENDING_DOCUMENTS`** (after all required nested doc steps are complete) or from legacy **`PENDING_GAF` / `PENDING_PARKING_REQUEST` / `PENDING_PET_REQUEST`** — not from backward recovery edges such as **`PENDING_SD_REFUND` → `READY_FOR_CHECKIN`**.

**Booking edit form parity:** `BookingEditForm` reuses the guest-form date/time UX for `check_in_date`, `check_out_date`, `check_in_time`, and `check_out_time` (calendar popovers + `type="time"` inputs). While **Edit Booking** is open and the row is revert-eligible, **`ReadyForCheckinSensitiveFieldsNotice`** shows a **short** amber alert only when the draft differs from the server on a workflow-sensitive field (saving then sets **`PENDING_REVIEW`**); there is no always-on banner in view mode. **Guests:** view mode **`Guests`** card lists primary + guests 2–4 with name, age, and valid-ID preview (18+); edit mode **`Guest Identity`** + **`Additional Guests`** expose the same fields with **`BookingGuestDocReplacer`** upload/replace per guest (`valid_id`, `guest2_valid_id`, …) — uploads save immediately via **`upload-booking-asset`** and may revert pipeline status when replacing guest docs.

**Legacy links:** URLs like `/?bookingId=<uuid>` are handled on `CalendarPage`: the app **`replace`** navigates to **`/form?bookingId=...`** (other query params are preserved).

## 5. User flows

### 5.1 New booking (typical production)

1. User opens **`/calendar`** (optionally **`?property=<slug>`**, **`?source=airbnb`**, etc.), selects check-in and check-out (respecting booked ranges and past dates), then **Proceed** → navigates to **`/form`** with the **same** non-date query params preserved plus **`checkInDate`** / **`checkOutDate`** (e.g. `/form?source=airbnb&checkInDate=YYYY-MM-DD&checkOutDate=YYYY-MM-DD`). Marketing home **`/`** does not host the picker; **`/?property=`** redirects to **`/calendar?property=`**.
2. On `GuestForm`, those query params seed React Hook Form defaults via **`getGuestFormDefaultValuesFromSearchParams`** (`guestFormData.ts`); in non-prod, **`handleGenerateNewData`** still runs **`generateRandomData`** on load (dummy names/files), then reapplies normalized **`checkInDate` / `checkOutDate`** and **`numberOfNights`** from the URL when both params are present so the calendar range is preserved. The dev **Generate New Data** control calls the same helper without preservation so dates randomize too.
3. On `GuestForm`, a **new `bookingId`** is generated client-side (`crypto.randomUUID()`) when `bookingId` is absent from the URL.
4. User fills the form; files are appended to `FormData` with deterministic names via `handleFileUpload` in `ui/src/utils/text/helpers.ts`.
5. Submit calls **`POST {VITE_API_URL}/submit-form`** with Supabase anon key headers. `submit-form` persists booking data/files (**no PDF** on submit). It **does not send workflow emails** (booking acknowledgement, GAF request, pet request, parking broadcast — those are only from `WorkflowOrchestrator` when an admin transitions **`PENDING_REVIEW → PENDING_DOCUMENTS`**). When **`sendEmail` is not `false`** (default: send; guest **Developer Controls** pass explicit `sendEmail=true|false`), after a successful **database** save it sends **`sendNewBookingRequestNotify`**: **New Booking Request** HTML to **`EMAIL_REPLY_TO`** only (`emailService.ts` + `new-booking-request.html`), with **`reply_to`** set to the guest’s email; failures are logged and do **not** fail the guest submit. The early **`🎛️ API Action Flags`** line only means `sendEmail` is allowed — it is **not** proof the email was sent; look for **`[submit-form] New booking request notify ok`** (includes Resend id), **`... skipped`**, or **`... failed`** later in the same request logs.
6. Edge function checks **date overlap** against active (non-canceled) rows, then processes.
7. On success, UI navigates to **`/success?bookingId=...`** with `location.state.bookingData` for the summary card.

### 5.1.1 Airbnb source differences

When the guest form URL includes **`?source=airbnb`** (case-insensitive), the booking is treated as an Airbnb booking (`booking_source = 'Airbnb'`). **`?source=facebook`** sets `booking_source = 'Facebook'`. With **no `source` param**, bookings default to **`Direct`** (neutral name label on the form; no Payment step change).

Key differences from non-Airbnb bookings:

- **Guest form** step list is filtered by property **`properties.settings`** toggles **`allowParking`**, **`allowPets`**, **`allowSurpriseDecor`** (resolved via **`get-guest-payment-info`**; default all `true`). When off, the step/checkbox is hidden and **`submit-form`** forces the field false.
- **Guest form** Stay-step **check-in/out time defaults** and early/late warning thresholds come from the same **`get-guest-payment-info`** payload (`checkInTime` / `checkOutTime`, 24h `HH:mm`; property-settings defaults **`14:00`** / **`12:00`**). Existing **`?bookingId=`** loads keep stored submission times from **`get-form`**.
- **Guest form** guest-list **capacity** (`maxAdults`, `maxChildren`) comes from the same payload (set by property **Unit type** under development **`unitTypes`** presets). Reminder banner + **`submit-form`** occupancy checks use building rule: age 4+ = adult, age 0–3 = child.
- **Guest form** is **4 steps** for Airbnb (Payment step hidden). Non-Airbnb Direct/Facebook bookings include Payment unless parking/pets toggles remove middle steps. `paymentReceipt` is optional in the Airbnb schema; `findUs` defaults to "Airbnb" when `?source=airbnb`.
- **Server (`submit-form`)** allows missing `paymentReceipt` file and skips the downpayment receipt AI validation for Airbnb submissions.
- **Admin `ReviewPricingForm`** defaults down payment and security deposit to **₱0** (editable by admin if needed).
- **Admin `BookingEditForm`** hides the Downpayment receipt row in the Documents section for Airbnb bookings.
- **Ready-for-check-in email** hides the Payment breakdown table and payment QR section when total balance due is ₱0 (source-agnostic — applies to any booking with zero total balance).
- **Guest balance settlement** (`READY_FOR_CHECKIN` → `READY_FOR_CHECKOUT`): for Airbnb, **booking rate / down payment / security deposit are excluded** from total guest balance — only **pet fee** and **additional guest fee** count. When that total is ₱0, **paid = 0** and **no payment balance receipt** is required. Additional fees still require a GCash/Maya/bank/cash receipt with AI validation.
- **SD refund flow** is skipped when `security_deposit = 0`: booking goes directly from `READY_FOR_CHECKOUT` to `COMPLETED` (no SD form email, no guest `/sd-form` step). The `sd-refund-cron` also suppresses the check-out email for SD=0 bookings.

### 5.2 View / update existing booking

1. URL is **`/form?bookingId=<uuid>`** (or legacy **`/?bookingId=<uuid>`**, which redirects to `/form` as above). The id is sanitized on client and server if query junk is appended.
2. `GuestForm` loads data via **`GET {VITE_API_URL}/get-form/{bookingId}`** and hydrates the form; image fields use URLs from the API for previews. Response includes **`guestCanUpdate`** — **`false`** when `status !== PENDING_REVIEW` (form is read-only; **`submit-form`** rejects updates server-side).
3. On submit, server loads raw row, runs **`compareFormData`**; if **no changes**, returns `{ success: true, skipped: true }` and UI still redirects to success (no DB/email/calendar/sheet work — **no New Booking Request notify**).
4. If changes exist, row is updated; calendar event is found by `privateExtendedProperty` `bookingId`, deleted, recreated; sheet row is located by booking ID in column A and updated. **No workflow emails** are sent from `submit-form` updates; the **New Booking Request** notify to **`EMAIL_REPLY_TO`** follows the same **`sendEmail`** rule as new submits (default on when the query param is omitted).
5. Status revert rule for updates: revert to `PENDING_REVIEW` only when the row is in **`PENDING_DOCUMENTS`**, **`PENDING_GAF`**, **`PENDING_PARKING_REQUEST`**, **`PENDING_PET_REQUEST`**, or **`READY_FOR_CHECKIN`** (not when already `PENDING_REVIEW`, in SD refund stages, `COMPLETED`, or `CANCELLED`), the update is from public `/form` or admin `/bookings/:bookingId`, **and** at least one workflow-sensitive field changed. The **same row update** applies **`pendingDocumentsClearPatchForGuestEditRevert`** (`statusMachine.ts`; UI mirror `bookingStatus.ts`): nested Pending Documents completion timestamps, manual-incomplete flags, approved and request PDF URLs, **admin parking settlement** (`parking_rate_paid`, `parking_owner`, `parking_owner_email`, `parking_endorsement_url`), and **guest balance settlement** (`guest_balance_paid_amount`, `guest_balance_payment_receipt_url`). **Pricing snapshot fields** (`booking_rate`, `down_payment`, `balance`, `security_deposit`, `pet_fee`, `parking_rate_guest`, `guest_additional_fee`) are **left unchanged** on revert so the Pending Review pricing card keeps the last submitted values. **`WorkflowOrchestrator`** merges the **same patch** at the start of **`PENDING_REVIEW → PENDING_DOCUMENTS`** or **`PENDING_GAF`** before **`TransitionPayload`**, clearing stale document pipeline columns without wiping pricing (payload may still overwrite pricing on that transition). Independently, **`isSubStatusCompletedInStepper`** (`workflow.ts`) forces nested rows to **Incomplete** whenever `status === PENDING_REVIEW` so the progress UI never shows stale green checks after a revert.
   - Facebook/Airbnb name, primary guest name, email, phone number
   - Additional guest names
   - Check-in/check-out dates or times
   - Parking details
   - Pet details
   - Downpayment receipt, valid ID, pet vaccination, or pet photo uploads
   - If only other fields changed, keep the current status.
6. Admin replacement of guest documents (`upload-booking-asset` with `payment_receipt`, `valid_id`, `pet_vaccination`, or `pet_image`) while the booking is in the same revert-eligible statuses as (5) also sets status back to `PENDING_REVIEW` and applies the same **`pendingDocumentsClearPatchForGuestEditRevert`** merge in one update (same rationale as receipt/ID changes on the public form).

### 5.3 Calendar and availability

- **`get-booked-dates`** returns `{ id, checkInDate, checkOutDate }` for rows where **`status` is not `CANCELLED`** (and not legacy `'canceled'` in JS), and **check-out date ≥ start of today** (past stays are omitted for picker performance). Dates are normalized to `YYYY-MM-DD` in the JSON payload.
- **Overlap rule** (submit + DB check): **`DatabaseService.checkOverlappingBookings`** treats only **`CANCELLED`** / legacy **`canceled`** as non-blocking; all other statuses (including **`COMPLETED`**) block overlaps. Same-day turnover: overlap is false if new check-in equals existing check-out or new check-out equals existing check-in.
- **`NEW_FLOW_PLAN.md` §6.1 Q7.2:** only **`CANCELLED`** frees dates for overlap; **`COMPLETED`** still blocks when the row is in scope of the query (future check-out in `get-booked-dates`; overlap check uses full non-cancelled set).

### 5.4 Dev UX (guest form)

- **`VITE_NODE_ENV === 'production'`** is treated as production build; otherwise non-production.
- **Dev controls** (save to DB, storage, **Send email** on submit) show when **`!isProduction`** on `/form` (never via `?dev=true`); **every checkbox defaults to checked** (uncheck to skip). Flags are sent as **FormData** fields on `submit-form` — not browser or API URL query params. Hosted production (`DENO_DEPLOYMENT_ID`) always forces the full happy path server-side. They do not gate workflow emails or PDFs on the public form; those run from the admin booking detail → `transition-booking` / `workflowOrchestrator`.
- Checkbox FormData fields: `saveToDatabase`, `saveImagesToStorage`, `sendEmail` (each `true`/`false`). **`sendEmail`** gates only the **New Booking Request** owner notify (`EMAIL_REPLY_TO`). **Filled GAF / pet request PDFs** are not produced on `submit-form`. **Defaults:** every dev toggle starts **checked** (full happy path); operators uncheck to skip. Deprecated URL keys (`dev`, `testing`, legacy `updateGoogleCalendar` / `updateGoogleSheets`, and those flag names) are stripped from guest/calendar URLs on load.
- **No test-booking mode**: there is no `?testing=true`, no `is_test_booking` column, and no `[TEST]` / `TEST_` prefixes in storage or email subjects. Use a **local or staging** Supabase project for safe end-to-end trials.
- **Cancel booking**: `POST /cancel-booking` with `{ bookingId, confirm: true }` (admin JWT required). Routes through `WorkflowOrchestrator` which sets DB `status` to `CANCELLED` — **does not delete** assets or DB row.

### 5.5 Error recovery (guest-friendly)

On submit error, Sonner toast can include **copy booking info** (text format from `formatBookingInfoForClipboard`). Dev controls include **paste from clipboard** to repopulate fields using `parseBookingInfoFromClipboard` (files still required).
