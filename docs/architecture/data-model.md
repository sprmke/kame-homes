## 6. Data model (`guest_submissions`)

**`organizations`** / **`properties`** (migration **`20260629180000_multi_tenancy_foundation.sql`**; **`tower`** + **`unit_number`** + global unique pair in **`20260821140000_properties_tower_unit_columns.sql`**; **`properties.slug`** globally unique in **`20260821150000_properties_slug_globally_unique.sql`** — required because guest **`?property=`** resolves by slug alone): single-owner orgs (`owner_id` → `auth.users`), properties per org (`organization_id`), slug-based URLs. **`tower`** is one of `Monaco` \| `Bali` \| `Barbados`; **`unit_number`** is exactly four digits; **`tower_and_unit`** remains the display string (`Monaco 2604`). **Today:** duplicate tower+unit pairs are rejected on **`create-organization`**, **`create-property`**, and **`update-property`** regardless of status. **Planned ([#120](https://github.com/sprmke/kame-homes/issues/120)):** uniqueness only among **`ACTIVE`** properties so successive sublessees / hosts can reuse the same unit after prior listings are **`INACTIVE`**. Display **name** uniqueness is **per organization** (not a cross-host lock). **`guest_submissions`**, **`finance_line_items`**, **`maintenance_items`**, and singleton settings tables gain optional-then-required **`property_id`**; default backfill assigns **Kame Home** / **Monaco 2604**.

**`property_blocked_dates`** (migration **`20260801120000_property_blocked_dates.sql`**): owner-managed unavailable night ranges per property. Columns: `id`, `property_id`, `start_date`, `end_date`, optional `note`, `created_at`, and nullable `created_by`; `end_date > start_date` and ranges use checkout-exclusive **`[start_date, end_date)`** semantics. Admin writes use **`property-pricing`** with `pricing:view` / `pricing.rates:edit` / `pricing.blocks:add` / `pricing.blocks:delete` (legacy stored `pricing:edit` still expands); partial unblocks call transactional RPC **`unblock_property_blocked_dates`** (migration **`20261001150000_unblock_property_dates_function.sql`**) so remaining range segments are preserved. Public **`get-booked-dates`** returns these ranges alongside bookings, and **`submit-form`** rejects blocked nights server-side.

**Calendar sync — Airbnb / OTA two-way iCal** (`calendarSync` plan feature, **Pro / `growth` and above**; migrations **`20261213120000_calendar_sync_feeds.sql`** … **`20261213120500_calendar_sync_cron.sql`**). **`property_calendar_feeds`**: one inbound `.ics` import feed per row — `property_id` (FK CASCADE), `provider` (`airbnb` \| `booking_com` \| `vrbo` \| `other`), `label`, `ics_url_encrypted` (AES-256-GCM via `_shared/secretsCrypto.ts`, never returned raw — `calendar-sync-settings` masks it), `is_active`, `create_bookings` (Phase 2 opt-in; forced `false` in Phase 1), plus poll-state columns `last_attempted_at` / `last_success_at` / `last_error` / `consecutive_failures` / `empty_pull_streak` / `last_etag` / `last_modified_header` / `last_feed_hash`. **`property_calendar_export`**: one row per property — `token` (unguessable, in the public export URL), `is_enabled`, `rotated_at`, `last_served_at`; the outbound feed at **`ical-export`** (`?property=<slug>&token=<t>[&as=<provider>]`) publishes GFM's busy nights (bookings + manual blocks), and `?as=<provider>` omits that provider's own imported rows to prevent an echo loop. **`property_blocked_dates`** gains **`source`** (`'manual'` \| `'ical_import'`, default `'manual'`), **`feed_id`** (FK CASCADE), **`external_uid`**, **`external_summary`**, **`last_seen_at`**, with a unique partial index on `(feed_id, external_uid) WHERE feed_id IS NOT NULL`; `unblock_property_blocked_dates` gains a third `p_source_filter text DEFAULT 'manual'` arg so existing 2-arg callers never touch synced rows. `ical_import` blocks are read-only in the Pricing calendar (not selectable / not unblockable) and clear only when the feed drops them or the feed is removed. **`calendar_sync_events`**: per-run audit trail — `feed_id`, `run_id`, `external_uid`, `action` (`block_created` \| `block_updated` \| `block_removed` \| `booking_created` \| `booking_cancelled` \| `booking_rescheduled` \| `conflict_detected` \| `skipped` \| `error`), `start_date` / `end_date` / `summary`, `blocked_date_id` / `booking_id` (FK SET NULL), `detail` jsonb. `notifications_type_check` widened with **`calendar_sync_failing`** (emitted at exactly `consecutive_failures = 4`) and **`calendar_conflict`**. Pull cadence: hosted `pg_cron` job **`calendar-sync-every-30m`** → **`calendar-sync-cron`** (see [[edge-functions]] and [[scheduled-jobs-and-testing]]).

**Calendar sync Phase 2 — reservation ingestion + guest-form completion** (migrations **`20261214120000`** … **`20261214120200`**). When a feed sets **`property_calendar_feeds.create_bookings = true`**, `calendar-sync-cron` also promotes each reservation `VEVENT` to a real **`guest_submissions`** row: **`external_source`** (`airbnb` \| `booking_com` \| `vrbo` \| `other`), **`external_uid`** (the reservation UID, sync identity), **`external_feed_id`** (FK SET NULL), **`external_raw`** jsonb (reservation URL, phone last-4), with a unique partial index on `(external_feed_id, external_uid)`. `booking_source` stays `'Airbnb'` (reuses the existing zero-payment / no-SD-refund branch). **Rows are created in `PENDING_REVIEW` and never auto-advanced** by the sync engine — it only creates, reschedules (guarded revert to `PENDING_REVIEW`), or cancels (via `WorkflowOrchestrator`, unless the stay is already past check-in — logged `past_checkin_feed_drop`). Every guest-facing side effect is suppressed while `guest_email` is blank (`workflowOrchestrator.ts` + `sd-refund-cron`). The host then forwards **`<origin>/form?complete=<token>&property=<slug>`** to the OTA guest to fill in the rest: **`guest_form_token`** (unique partial index), **`guest_form_token_issued_at`**, **`guest_form_completed_at`** — minted by `issue-guest-form-completion-token`, resolved by `get-form-completion`, submitted through `submit-form-completion` (UPDATE-only; stored dates win; status stays `PENDING_REVIEW`). `notifications_type_check` also gains **`booking_external_imported`** and **`booking_guest_form_completed`**.

**`parkings`** / **`parking_settings`** (migration **`20260918120000_parkings.sql`**): one row = one parking slot per org (`organization_id`). **`slug`** globally unique; physical slot uniqueness on **`(residence_name, tower, level, slot_label)`**. **`parking_type`**: `inside_tower` \| `outside_tower` \| `motorcycle`. **`accepted_vehicle_types`** (`TEXT[]`, `car` \| `motorcycle`, migration **`20261016120000_parking_accepted_vehicle_types.sql`**) drives broadcast candidate matching; car-size fit tiers (`compact`/`sedan`/`suv`/`van`) are derived via `resolveVehicleFit`, never stored. **`organizations.host_modes`** (`TEXT[]`, values `property` \| `parking`) tracks which asset types the org hosts. Standalone parking reservations: **`guest_submissions.parking_id`** (migration **`20260731120000_guest_submissions_parking_id.sql`**) — mutually exclusive with **`property_id`**; org **`list-bookings`** unions both. Guest-stay **`need_parking`** on property rows is unchanged.

**Parking broadcast** (migrations **`20261017120000_parking_booking_broadcast.sql`**, **`20261017130000_parking_broadcast_terminal_check_fix.sql`**, cron in **`20261018120000_parking_broadcast_expire_cron.sql`**; ranked batching in **`20261115120600_parking_broadcast_batching.sql`**, **`20261115120700_parking_broadcast_pinned_id.sql`**; payment in **`20261128120100_parking_payment.sql`**): `guest_submissions_status_check` widened with **`PENDING_HOST_ACCEPTANCE`** / **`NO_HOST_AVAILABLE`** / **`PENDING_PAYMENT`**; a broadcast row has **`parking_id IS NULL`** until claimed, only legal when **`parking_request_organization_id IS NOT NULL`** and status is one of the two new statuses (or the terminal `CANCELLED`). New `guest_submissions` columns: **`parking_request_organization_id`**, **`requested_vehicle_type`**, **`parking_broadcast_expires_at`** (TTL deadline, reset per batch), **`parking_broadcast_batch_number`** (active ranked-dispatch round, default 1), **`parking_pinned_id`** (set when the guest requested one specific listing directly — pinned requests stay single-round, never expand to other org parkings), **`parking_claimed_at`**, **`parking_endorsement_note`** (host-authored, shown to guest post-claim, ≤2000 chars), **`guest_auth_user_id`** (Phase 3 — the signed-in guest who submitted; ownership binding for pay-now/cancel), **`parking_payment_expires_at`** (Phase 3 — TTL for the `PENDING_PAYMENT` window). **`parking_booking_broadcasts`**: one row per candidate parking per broadcast batch — `booking_id`, `parking_id`, `batch_number`, `host_gross_at_broadcast` (ranking audit trail, never guest-facing), `response` (`pending`\|`claimed`\|`declined`\|`expired`), `notified_at`, `responded_at`. First-Accept-wins is enforced by a guarded `UPDATE guest_submissions ... WHERE status = 'PENDING_HOST_ACCEPTANCE'`, not by the broadcast table; batch advance/terminate uses the same guard idiom scoped additionally by `parking_broadcast_batch_number` — see **[[parking-workflow|Parking workflow]]** for the full status graph and race-safety rationale.

**Parking payment** (Phase 3, migration **`20261128120100_parking_payment.sql`**): claim no longer confirms immediately — it sets **`PENDING_PAYMENT`**, which only resolves to **`PENDING_REVIEW`** (paid & confirmed) via guest payment, or back to **`PENDING_HOST_ACCEPTANCE`** (payment-window timeout, search resumes) or **`CANCELLED`** (guest cancel) — never via the generic transition endpoint. **`parking_payment_transactions`**: `booking_id`, `parking_id`, `organization_id`, `guest_charge_total`/`host_gross_total`/`commission_pct`/`host_net_total`/`nights` (snapshotted at checkout-creation time from `platform_parking_settings` — Phase 4 replaced the Phase 3 interim flat-rate/10%-commission stubs; amounts are **per-night prorated**, not averaged), `provider`/`provider_reference`/`checkout_url`/`payment_method_type`, `status` (`pending`\|`paid`\|`failed`\|`expired`\|`cancelled`\|`refunded`), `failure_reason`, `raw_webhook_payload`. One `pending` row per booking (unique partial index) — mirrors `org_payment_transactions`'s shape and the same guarded-UPDATE/mark-failed-on-error idioms. Webhook dispatch (`paymongo-webhook` → `subscriptionOrchestrator.ts#handlePaymongoWebhookEvent`) now branches on `metadata.kind` (`'parking_booking'` vs `'org_subscription'`) before resolving a transaction — see **[[parking-workflow|Parking workflow]]**'s "Payment (Phase 3/4)" section for the full release-vs-cancel semantics.

**Parking platform config & payout ledger** (Phase 4, migration **`20261129120000_parking_platform_settings.sql`**): **`platform_parking_settings`** — singleton (`id = 1` CHECK, mirrors `platform_payment_settings`) holding `commission_pct`/`guest_rate_weekday`/`guest_rate_weekend`, resolved by `resolveParkingPlatformSettings()` and replacing the Phase 2/3 `STUB_*` constants everywhere (match-engine price cap, payment amount math, host-facing pricing cap). Same migration extends **`parking_payment_transactions`** with `disbursed_at`/`disbursed_by`/`disbursement_reference`/`disbursement_method` (`'manual'`\|`'paymongo_platforms'`, default `'manual'` — real split-payout not yet built) and `clawback_amount`/`clawback_reason`/`clawback_at`/`clawback_by` (audit trail only, no automated collection). Managed via the super-admin `/admin/parking/payouts` page — see **[[parking-workflow|Parking workflow]]**'s "Platform config & payouts (Phase 4)" section.

**Parking endorsement automation & escalation contact** (Phase 5, migration **`20261130120000_parking_endorsement.sql`**): New `guest_submissions` columns — `endorsement_sent_at` (guarded-update guard, set once `sendParkingEndorsementEmail` succeeds, never overwritten), `endorsement_send_error` (last failure reason, e.g. no PMO email configured for the matching development), `endorsement_email_snapshot` (exact rendered HTML sent, so the guest-facing in-app copy view is literal, not a re-render). No new recipient-config column: the PMO recipient is resolved via `loadDevelopmentPmoEmailByName(parking.residence_name)` against the existing `developments.name`/`settings.pmoEmail`. See **[[parking-workflow|Parking workflow]]**'s "Endorsement automation & communication (Phase 5)" section.

**`finance_line_items`** (migration **`20260527120000_finance_line_items.sql`**, …, parking scope **`20260919120000_finance_line_items_parking_id.sql`**): property- or parking-scoped **expense** / **income** transaction lines — exactly one of **`property_id`** or **`parking_id`** per row (`kind`, **`label`** (required), **`amount`** (required, &gt; 0), **`category`** (required), `occurred_on` DATE, `notes`, optional `receipt_path`, `created_by`, optional **`recurrence_series_id`** + **`recurrence_interval`** … (`daily` \| `weekly` \| `monthly` \| `twice_monthly` \| `every_2_months` \| `quarterly` \| `every_6_months` \| `yearly`), optional Telegram reminder columns (**`telegram_reminder_enabled`**, **`telegram_due_date`**, **`telegram_days_before`**, **`telegram_reminder_interval`** `hourly` \| `every_2_hours` \| `every_4_hours` \| `every_12_hours` \| `daily_noon`, **`telegram_message_template`**), optional **`paid_at`** (stops reminders for every interval when set). Recurring creates are **materialized** — one row per occurrence through **`recurrence_until`**; **`telegram_due_date`** on each row is that occurrence's **`occurred_on`** (bulk series PATCH does not overwrite per-row due dates). **`telegram-finance-cron`** sends at most **one** reminder per **`recurrence_series_id`** per tick.
