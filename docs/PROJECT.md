**Database connection topology:** four distinct connection paths, only one of which is high-fanout. (1) **All 300 edge functions** connect via `supabase-js` over **PostgREST/HTTP**, never a direct Postgres socket — pinned in `_shared/supabaseJs.ts` (`createClient`/`SupabaseClient` from `@supabase/supabase-js@2.38.4`, esm.sh). PostgREST maintains its own server-side pool; the classic "N serverless instances exhaust `max_connections`" failure mode does not apply the way it would with direct per-request Postgres connections. Service-role client creation is centralized through `_shared/orgAuth.ts#createServiceClient()` (a module-scope singleton, cached once per warm isolate — ~262 files / ~493 call sites depend on it) rather than per-call; a handful of other `_shared/*.ts` files (`aiCreditLedger.ts`, `aiUsageService.ts`, `documentRequirements.ts`, `telegramAdmin.ts`, and others — see doc 15 Phase 15.2 for the full list) still create a fresh client per call, identified but not yet fixed. (2) **`pg_cron` + `pg_net`** scheduled jobs (14 cron edge functions, `cron.schedule(...)` in `supabase/migrations/**`) run **in-database** — each job body is a `pg_net.http_post(...)` fire-and-forget call to an edge function, async and non-blocking from Postgres's side, not a held connection. (3) **Backup/restore scripts** (`scripts/deploy/backup-supabase.sh`, `rollback-supabase.sh`, `scripts/data/sync-prod-public-data-to-local.sh`) use a **direct/session-pooler** Postgres connection (`DEV_DB_URL`/`PROD_DB_URL`, session mode — port 5432, not the 6543 transaction pooler) via `pg_dump`/`pg_restore`/`psql`, required for `pg_dump`'s session-level features; `sync-prod-public-data-to-local.sh` actively warns if the URL looks like the wrong pooler mode or a direct-IPv6 host. (4) **Migrations** (`supabase db push` / `bun run db:migrate`) also connect directly and take an advisory lock for the duration — see `docs/archive/operations/migration-runbook.md` for how to detect/clear a stuck lock after a failed migration. **Role-level timeouts:** `statement_timeout = '20s'` and `idle_in_transaction_session_timeout = '30s'` are set on the three PostgREST-facing roles (`anon`, `authenticated`, `service_role`) via `supabase/migrations/20261316121600_request_role_statement_timeouts.sql`, so a stuck statement or crashed function cannot hold a pool connection indefinitely; the `postgres`/migration role is deliberately excluded since DDL/backfills legitimately run long. **Not verified from repo code — needs a human with hosted-dev Supabase dashboard access (or `mcp__supabase__` tools with real project credentials) to check:** the hosted project's actual `max_connections`, whether the PostgREST-facing pooler is in session or transaction mode, PostgREST's own `db-pool` setting, and peak concurrent connections under real load. `supabase/config.toml`'s `[edge_runtime] policy = "oneshot"` is a **local-CLI-only** setting (hosted Supabase reuses warm isolates across invocations instead) — do not read it as evidence of hosted behavior. Full analysis: [`docs/workflow/planned/production-readiness-checklist/15-database-connection-pooling.md`](workflow/planned/production-readiness-checklist/15-database-connection-pooling.md).

## Org Activity & Audit Log

One append-only **`activity_log`** table records every meaningful action across an org — team members, org owner, super-admins acting on the org, the AI dashboard assistant, guests on public pages, crons, webhooks — with actor identity + role snapshot, field-level diffs, `severity` (`info` \| `notice` \| `warning` \| `destructive`), and `org` / `property` / `parking` scoping. Modeled on `super_admin_audit_events` (no FKs so history survives parent deletes; RLS-on/no-policies; no RLS read path). **Writer** `_shared/activityLog.ts` — `logActivity` / `logActivityBatch` / `buildActorContext` / `diffRecord` / `ACTIVITY_ACTION_CATALOG` (the single source of truth for an action's category / severity / target type / summary shape, mirrored client-side in `ui/src/features/dashboard/activity/lib/activityCatalog.ts`). Fire-and-forget, never throws, single INSERT, `await` inline by default; bulk = one summary row. **Read** `list-activity-log` (`serveAuthenticated` + `verifyOrgAccess`, keyset-paginated, listing-scoped members see only their assigned listings) + `activity-log-export` (owner/admin CSV, gated on the **`activityLogExport`** plan feature — Starter+; in-app viewing stays ungated). **UI** at `/org/:orgSlug/activity`, `/org/:orgSlug/property/:propertySlug/activity`, `/org/:orgSlug/parking/:parkingSlug/activity` (`ui/src/features/dashboard/activity/`; the org feed virtualizes past ~30 rows via `@tanstack/react-virtual`) + a reusable `<EntityActivityHistory>` panel (embedded on the booking detail page, the org/property/parking **Settings → Activity** section, the org Manage Member dialog, and the finance / maintenance edit modals). ## Guest AI voice receptionist

Property-scoped, authenticated guest voice uses a direct browser-to-Gemini Live connection with a
server-minted `v1beta` constrained ephemeral token. The approved model is registered once in
`_shared/geminiLiveEphemeral.ts`; the browser receives a versioned connection descriptor and never
hardcodes a provider endpoint or model. The current provider model is `gemini-3.8-live`; Google
still classifies Live API and ephemeral tokens as Preview, so rollout remains allowlist-first with
a dated model review gate.

Session lifecycle is `connecting -> active -> ending -> ended`, with terminal `failed`,
`abandoned`, and `expired`. `reserve_voice_receptionist_session` serializes property and guest cap
checks. `voice-receptionist-session` acknowledges setup and heartbeats the lease;
records host handoff, and atomically deletes captions. `voice-receptionist-reaper` closes stale
leases and applies transcript retention. Client captions live only in
`voice_receptionist_transcript_turns` as `client_reported` / `unverified`; they never create
canonical outbound `social_messages`. Derived safety flags contain categories only and are cleared
with the captions.

Grounding is tiered in `_shared/guestReceptionistContext.ts`. Volatile or stay-specific facts use
the closed tools `get_property_facts`, `check_dates`, `get_inquiry_price`, `get_my_stay`,
`get_stay_guide`, and `handoff_to_host`. Platform controls live on
`ai_platform_global_settings`: allowed feature kill switch, deterministic rollout percentage and
property allowlist, cost estimate, and 1-90 day caption retention. Staging health uses
`voice-receptionist-canary`; it is disabled when `ENVIRONMENT=production` and persists the latest
model, protocol, token-mint latency, setup latency, and structured failure state for super-admins.
Fresh token-mint failures open a five-minute circuit breaker that hides voice entry while text chat
remains available; an active setup clears the unhealthy signal. The super-admin AI surface also
loads a service-role-only seven-day reliability rollup with p50/p95 startup, first-audio, tool,
session, and reconnect metrics plus completion and threshold alerts. Metric rows never contain
caption text, tool arguments, or tool results.

Secrets: `GEMINI_API_KEY` (or local-only rotation via `GEMINI_API_KEYS`),
`VOICE_RECEPTIONIST_CANARY_SECRET`, and `VOICE_RECEPTIONIST_REAPER_SECRET`.

## Smart Pricing (AI-assisted dynamic nightly rates)

`smartPricing` plan feature (**Pro / `growth` and above** — same gate shape as `calendarSync`). Property-level, managed from **Pricing → Smart Pricing**. A **deterministic** engine (**`_shared/smartPricingEngine.ts`**, pure/no-I/O) prices every future night: `base × cappedAlgo(dowDemand × seasonDemand × leadTime × bookingPace) × structural(seasonRule × orphanGap)`, clamped to a host `[min, max]` and rounded. **`ALGO_DEVIATION_CAP`** hard-limits how far the _learned/inferred_ signals may move a night — `±6% / ±12% / ±22%` by aggressiveness — before the host's own season/holiday rule (uncapped) is applied; a sub-2% move snaps back to base (deadzone, no rec row). `dowDemand`/`monthDemand` (from `_shared/smartPricing.ts#gatherHistoryFeatures`, ~24mo of `guest_submissions`) are blended toward neutral by `demandConfidence` (0→1, ramps with booking volume) and tightly clamped (`0.88–1.15` / `0.85–1.20`). Booking pace is an **upward-only** nudge that fires only above 85% forward occupancy and is **off by default** — low occupancy on a small listing is never read as a discount signal. Lead-time last-minute discounts are gentle (`−8%`/`−4%`) with no far-out premium. Thin history (`< 20` elapsed booked nights) suppresses lead-time + pace entirely and applies only a small fixed weekend premium. An optional Gemini pass writes a rationale and flags outliers; it never sets the raw numbers. Config in **`property_smart_pricing_settings`**; per-date output in **`property_smart_pricing_recommendations`**; each run audited in **`property_smart_pricing_runs`**. Edge fns: **`smart-pricing-settings`**, **`smart-pricing-preview`**, **`smart-pricing-apply`**, **`smart-pricing-cron`**. UI: **`SmartPricingDialog`** (`AdminDialogShell`, `42rem`) — settings (Strength / Limits / Apply) + preview (₱ totals, month heatmap, month-scoped drivers + tap-day factor lines via `smartPricingPreviewExplain.ts`; `explain: false` on preview). Applying closes the dialog; turning off confirms then clears. Plan: [`workflow/for-testing/smart-pricing-ai.md`](workflow/for-testing/smart-pricing-ai.md) · architecture: [`architecture/smart-pricing.md`](architecture/smart-pricing.md).

## Query result cache (doc 12, Phase 12.3)

Generic DB-backed read-through cache for expensive per-request aggregates that aren't safely
`Cache-Control`-publishable (private/tenant-scoped), shaped after `ai_platform_response_cache`
(`_shared/aiQuotaCache.ts`). **Table** `query_cache` (`cache_key` text PK, `payload` jsonb,
`scope_org_id`/`scope_property_id`/`scope_parking_id` for wholesale tenant purge, `computed_at`,
`expires_at`, `schema_version`) — migration `20261316121700_query_cache_table.sql`. **Helper**
`_shared/queryCache.ts`: `buildCacheKey()` (schema-versioned, scope-complete, hashed — takes an
explicit `permissionScope` argument that MUST be set for any endpoint whose result varies by
viewer permission, not just by org/property/parking id — a key missing that dimension can leak
one viewer's cached response to a differently-privileged viewer), `readThrough()` (get-or-compute
with a short-lived `computing` sentinel as a soft single-flight lock — documented as "first
request wins, close-together duplicates both compute," not true durable single-flight),
`purgeCacheByScope()`, `sweepExpiredCacheRows()`. **Wired call site:** `dashboard-stats` (admin
home dashboard aggregate, polled 60s by every open dashboard tab, backed by an unbounded
`select('*')` in `_shared/dashboardService.ts#computeDashboardStats`) — 45s TTL ±10% jitter;
org-scope requests fold the viewer's resolved `scopedPropertyIds`/`scopedParkingIds` into
`permissionScope` so a scoped org admin and an all-listings admin never share a cache entry.
**Invalidation** routed through `_shared/workflowOrchestrator.ts#transition()` (`purgeCacheByScope`
called alongside the activity-log/PostHog side effects, not sprinkled into handlers) — purges both
the property-scoped and resolved org-scoped entries on every saved transition. **Sweep cron**
`query-cache-sweep-cron`, nightly (`17 2 * * *` UTC / 10:17 Manila), deletes expired rows. Host
Analytics (`_shared/analyticsService.ts`) deliberately keeps its own "compute on read, no rollup
table" design (see above) — this cache does not change that; analytics rollups remain a documented
follow-up if live `pg_stat_statements` data later shows analytics itself is the worst offender, not
a decision reversed in this pass. Not yet wired: `financeService.ts`, `propertyListStats.ts`,
`publicSearch.ts`, `publicListingFacets.ts`, `superhostMetrics.ts`, `smartPricingEngine.ts`,
`inboxThreadMetrics.ts` — see doc 12's Implementation status for the reasoned-but-unmeasured
prioritization. Edge fns + data model: [`architecture/edge-functions.md`](architecture/edge-functions.md#query-result-cache-query_cache-table); cron: [`archive/operations/scheduled-jobs-and-testing.md`](archive/operations/scheduled-jobs-and-testing.md); plan: [`workflow/planned/production-readiness-checklist/12-cache-expensive-queries.md`](workflow/planned/production-readiness-checklist/12-cache-expensive-queries.md).
