# Tier/feature alignment audit — gate every page to the current plan

## Context

[Host Plans & Pricing Tiers](../done/host-plans-and-pricing-tiers.md) and [Feature Gating & Subscription Upgrade](../done/feature-gating-subscription-upgrade.md) shipped a real entitlements platform on 2026-08-18: `pricing_plans.features` (JSONB, typed by `supabase/functions/_shared/planFeatures.ts`), `property_subscriptions`, and server-side resolution via `resolvePropertyEntitlements` (`_shared/planEntitlements.ts`). On the client, `useFeatureGate`/`FeatureGate`/`RequirePropertyFeature`/`RequirePropertySubscriptionAccess` (`ui/src/features/dashboard/plans/`) and `UpgradeModalProvider` are wired to it, and a few surfaces gate correctly end-to-end (team invites, inbox auto-reply, voice receptionist).

The gap: gating was applied where each feature was originally built, not swept across the app afterward, and several modules were never gated at all. Confirmed example — `BookingDetailTabs.tsx` renders the "AI Summary" tab unconditionally; only the **run** action inside `BookingAiSummaryPanel.tsx` checks `useFeatureGate('aiValidations')`. A research pass across finance, maintenance, marketing, notifications, inbox, templates, public pages, and settings found the same pattern repeated, and — more seriously — found that **several of these are client-only gates with no server-side check at all** (finance/maintenance export, marketing publish/generate/template-save, Telegram save/test, Meta inbox connect, quick replies). Anyone who strips the UI overlay in devtools can use those today regardless of plan.

This plan: audits and fixes gating on every page/module, makes new specific tier assignments the host has decided on, hardens every gate with a matching **server-side** check (this is the load-bearing part — UI gating is UX, not security), adds a professional tier-badge system, redesigns the upgrade modal to be dynamic and to support mid-plan upgrades with proration, extends gating into booking-workflow automation, and implements the already-designed [org-level portfolio bundling](./pricing-portfolio-bundling.md).

**Downgrade-safety policy** (governs every fix in this plan):

- Losing entitlement must hide or disable the ability to **create/run/use** a feature going forward — never leave it silently usable.
- It must **never delete or hide data that already exists** (a past AI summary, a saved marketing draft, uploaded receipts, etc.) — that data stays visible, read-only, with an upgrade CTA to regain the interactive capability.
- Re-upgrading restores full functionality with no data loss.

**Preview-open policy** (new, per host direction for inbox/templates): some UI should stay **explorable** on a lower tier even though the underlying action is gated — quick replies and inbox automation panels, template placeholders/reset, marketing preview canvases — so the host can see what a paid tier unlocks. The distinction: read/browse/preview stays open; save/enable/generate/publish is what's gated. Apply this pattern consistently wherever it fits, not only in the modules that mentioned it explicitly.

**Web/normal chat tier — analysis and decision** (host asked me to decide): keep it **Free**. Reasoning: guest messaging is the core operational loop this product is built around — a guest submitting the booking form needs a way to reach the host about check-in/check-out issues regardless of plan, and the booking workflow itself (statuses, forms, PDFs) is already free-tier accessible. Gating basic communication would break that loop and hurt free-to-paid conversion rather than help it (a host who can't talk to their guest won't stick around to see the AI features that would convince them to upgrade). This mirrors the notifications decision (in-app stays free, the higher-leverage Telegram integration is paid) and the inbox decision the host already made (Meta — an external premium channel — is Business tier). What's monetized is the _productivity/automation layer on top of_ chat: quick replies (Starter+) and AI auto-reply (already gated, existing `aiChatAutoReply`), not the ability to chat at all.

## Phase 4 — Server-side enforcement hardening (security) ✅ done 2026-08-24

Closing this properly needs field-level discrimination inside those shared handlers — bigger and riskier than this phase's scope, and not in the plan's original "confirmed real gaps" list. A Free-tier host could theoretically bypass the client's inert-autosave/manual-save-blocks-persisting behavior for brand color, description, house rules, cancellation policy, social links, or stay-guide template text specifically by calling these shared endpoints directly — lower severity than the Phase 4 items above (it's "edit your own free-tier-eligible settings a bit early," not a data leak or third-party-cost issue), but real. Flagged here for whoever picks up that follow-up rather than left implicit.

**This phase is not optional polish — it's the actual security boundary.** Per this repo's own rule (`CLAUDE.md`: "RLS is not the access-control layer today — it's edge-function checks"), a client-only gate is cosmetic: removing a CSS overlay or disabling a React component in devtools bypasses it entirely, and the underlying edge function will still execute the paid action for a free-tier property. Research confirmed this is true **today** for: finance/maintenance export, marketing publish (`publish-to-meta`), marketing generate (`generate-marketing-template`/`generate-marketing-caption`), marketing template save (`marketing-templates`), all `telegram-*-settings` functions (`requireTelegramNotificationsEnabled()` already exists in `planEntitlements.ts` but has zero callers), Meta inbox connect (`meta-inbox-oauth-start`/`callback`/`complete`), and quick replies.

3. New feature keys from Phase 2 (`financeReporting`, `maintenanceReporting`, `metaChatChannel`, `quickReplies`, `customTemplates`, `publicPagesAutosave`) each need their server-side check added at the same time their edge function is touched — don't ship a client gate without its server pair in the same change.
4. For features where the underlying data is already visible to the user regardless of plan (e.g. finance/maintenance numbers are shown on-screen on Free; only the PDF export convenience is paid) — still add the server check for integrity, but note in the matrix that these are lower-severity (bypassing them recreates a report manually from visible data, not a data-access leak) versus features that generate new resources or reach a third-party integration (Meta connect, marketing generation, Telegram) where a bypass has real cost/liability and must be treated as high-severity.
