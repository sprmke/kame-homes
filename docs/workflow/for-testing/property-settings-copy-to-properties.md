# Copy property settings to other properties

## Goal

Let a host reuse one property's configuration across their other properties without redoing setup unit by unit. From the org **Properties** page a host picks a **source** property, selects which configuration groups to copy (pricing, marketing designs, templates, notification/bot config, guest-form toggles, house rules, amenities, cancellation policy, public-page design, voice/AI settings, custom team roles, recurring finance/maintenance items, …), picks one or more **target** properties, reviews a per-target summary of what will change (including anything skipped because the target's plan or the actor's permissions don't allow it), and confirms. The operation copies **configuration and settings only** — never bookings, guests, finance/maintenance actuals, team members, Meta connections, plan/billing, calendars, reviews, or any other per-listing operational data. A server-side registry defines exactly what each group reads, how identity/data is stripped, and how it is written to each target, so "what is copyable" is one auditable list.

## Review findings (verified against the codebase 2026-09-06)

The first draft was checked against migrations, edge functions, and shared services. Corrections folded into this version:

1. **Reuse existing seeding infra — do not re-implement row creation.** `create-property` already calls `seedPropertySettings()` (`supabase/functions/_shared/propertySettingsSeed.ts`) + `seedPropertyTeamTemplates()` (`_shared/propertyTeamTemplates.ts`). Both are idempotent and already handle the integer-`id` PK quirk on `app_settings` / `telegram_*_settings` (insert, then bump `id` on `23505`). The clone calls `ensurePropertySettings(targetId)` first so every backing row exists, then does **UPDATE**s only — sidestepping the PK/`CHECK (id = 1)` question entirely.
2. **Auth helper is `verifyPropertyAccess(req, propertyId, leaf?)`** from `_shared/orgAuth.ts` → `{ user, property, org, accessKind, permissions }`. It takes an explicit id, so the batch calls it once per (target, leaf). The `resolveScopedPropertyAccess` helper used by `app-settings` / `voice-receptionist-settings` reads a single `?property_id=` query param and is **not** usable for a multi-target batch — the copy function must not route through it.
3. **`app_settings` is one row per property (`app_settings_property_id_unique`) but backs 8+ groups** (pricing, branding/socials, vouchers, email automation, building forms, payment, GAF). Its groups **must** use curated per-group column allowlists. Single-purpose tables (`telegram_*_settings`, `ai_platform_property_settings`, `property_smart_pricing_settings`, `voice_receptionist_settings`, `custom_pages`, `public_page_configs`, `property_template_contents`) can use a **column denylist** (`id`, `property_id`, `organization_id`, `created_at`, `updated_at`, + credentials). This split is now explicit in §2.
4. **Only payment methods are OTP-gated.** `SETTINGS_VERIFICATION_ACTION = 'payment_settings'`; the OTP token binds to a `patchFingerprint` computed from the payment-methods array **and** one property. A batch to N targets needs N fingerprints / N verifications. → **`payment` is out of v1** (its own follow-up). GAF/building-form text + signature and email automations are **not** OTP-gated and are safe to copy.
5. **Drop the `aiAssistant` clone group.** `ai_dashboard_assistant` is org-level only (`ai_dashboard_assistant_org_settings` keyed by `organization_id`; the only per-property surface is a `disabled_property_ids UUID[]` toggle). Nothing per-property to copy.
6. **Voice receptionist config lives in `ai_platform_property_settings.feature_configs.voice_receptionist`** (JSONB), not `voice_receptionist_settings` scalar columns. `voiceReceptionist` and `aiOverrides` groups share `ai_platform_property_settings` — write through the existing service helpers (`_shared/voiceReceptionistService.ts#updateVoiceReceptionistSettings` and the `ai-platform-property-settings` patch path) so a JSONB deep-merge never clobbers the other group.
7. **`custom_pages` / `public_page_configs` `page_type` enums widened over time** (base allowed only `stay_guide`, then `property_landing`, then `property_showcase`). The clone enumerates the source's **actual rows** — never a hardcoded page-type list. Both have `UNIQUE (property_id, page_type)` and are lazily created → clone = upsert on that constraint. Strip `published` from showcase `config`.
8. **`app_settings` has an in-memory TTL cache** (`invalidateAppSettingsCache(propertyId)`); call it for every target after writing. Same discipline for other cached shared readers touched (email branding, entitlements).
9. **No multi-statement transactions from an edge function.** Writes are per-(target, group) and individually atomic at best. The contract is **idempotent, re-runnable, best-effort with a full per-target/per-group result**. Groups that touch several rows atomically (recurring finance/maintenance series, team roles) get an optional `plpgsql` RPC in a later phase for true atomicity.
10. **Telegram tables carry more columns than their base `CREATE`** (later migrations added `notify_on_daily_default`, `daily_reminder_times_manila`, …). The denylist approach is future-proof; still always exclude `bot_token_encrypted`, `chat_id_encrypted`, `google_calendar_id`, `google_spreadsheet_id` unless the credential opt-in is set. The shared bot token is `app_settings.telegram_global_bot_token_encrypted` (AES-256-GCM, shared env key → copying ciphertext works).
11. **Entry-point permission:** there is no `org:properties:configure`. Gate the menu item on the actor having ≥1 target they can edit; real enforcement is the per-(target, group) leaf check in the edge function. No new permission id.
12. **`property_custom_roles`**: `UNIQUE (property_id, lower(trim(name)))`. Seeded templates (Full Access / Operations / Read Only) already exist on every target via `seedPropertyTeamTemplates` → they collide → only genuine custom roles copy. Validate each permission id against the live catalog (`_shared/propertyTeamPermissions.ts`) and drop removed/unknown leaves. Check `20261231140100_org_team_template_role_ids.sql` for role-id shape changes before implementing.

## Scope

### In

- New **Copy settings** entry in the `OrgPropertyActionsMenu` (⋯) on `OrgPropertyCard` / `OrgPropertyListRow`, plus a header action on the org Properties page. Source = the property whose menu was opened (or a picker when launched from the header).
- `CopyPropertySettingsDialog` — 4 steps: **Source** → **What to copy** (grouped checkbox tree) → **Targets** (multi-select of the org's other properties, "Select all") → **Review & confirm** (per-target change/skip summary from a dry run).
- New edge function `copy-property-settings` (POST) driven by `_shared/propertySettingsClone.ts` (the registry).
- `_shared/propertyAssetClone.ts` to duplicate Storage objects (gallery media, GAF signature, template section images) into the target's path and rewrite URLs (Phase 2).
- `property_settings_copy_log` table + in-app notification + email notice to org owner / affected target teams.
- Per-target enforcement: `verifyPropertyAccess` on the source (`settings:view`) and on every target for each selected group's edit leaf; plan-feature gate per group per target — **skip + report**, never hard-fail the batch.
- Phased delivery: Phase 0 foundation → Phase 1 safe groups end-to-end (shippable on its own) → Phase 2 asset groups → Phase 3 recurring items → Phase 4 polish + dry-run diff.

### Out

- **Parking** listings (separate vertical). Registry pattern can extend to parking later.
- Cross-organization copy (targets are always same-org, enforced by comparing `organization_id`).
- Any **operational data** (full SKIP list in §2). Non-negotiable.
- **Plans / subscriptions / entitlements** — billing is org-level with per-property assignment (`org_subscription_properties`); targets keep their own plan and the copy respects it.
- **Team members / invitations** — only custom **role definitions** copy.
- **Announcement read state** — per-org, per-host, device-local (`hostAnnouncementReadState`); explicitly excluded, no change.
- **Payment methods** — deferred (OTP fingerprint is per-property; see finding 4). Own follow-up plan.
- A generic "duplicate this whole property" / new-property-from-template flow.

## Approach

### 1. Copyable-surface registry (the core) — `_shared/propertySettingsClone.ts`

Exports an ordered list of **groups**. Each group:

```ts
type CloneGroup = {
  id: CloneGroupId; // stable key used by UI, log, dry run
  label: string;
  editLeaves: TeamPermissionId[]; // required on every target
  planFeature?: PlanFeatureKey; // gated per target; skip+report when off
  assets?: boolean; // needs propertyAssetClone
  defaultOn: boolean; // UI initial state
  read(sourceCtx): Promise<GroupPayload>;
  sanitize(payload, targetCtx): GroupPayload; // strip identity + data + dead refs; clamp to target limits
  hasNonDefault(targetCtx): Promise<boolean>; // review hint ("already customized")
  write(payload, targetCtx): Promise<void>; // idempotent replace on target
};
```

`sanitize` removes identity. **Always stripped / recomputed on the target**, every group: `name`, `slug`, `type`, `tower`, `unit_number`, `residence_name`, `address`, `settings.{city,province,country,zipCode,latitude,longitude,mapsUrl,placeId}`, `app_settings.gaf_tower_and_unit_number` (recomputed from the target's tower+unit), `public_guest_app_origin`, every `id`/`property_id`/`organization_id`, storage paths (re-derived), OTA/Meta identifiers.

**Write model:**

- `app_settings` groups → curated column allowlist, one `UPDATE ... WHERE property_id = $target` after `ensurePropertySettings(target)`; then `invalidateAppSettingsCache(target)`.
- Dedicated-table groups → column denylist copy via the table's existing service helper where one exists, else a scoped `UPDATE`.
- Multi-row groups (templates, telegram-per-module, custom roles, recurring series) → delete-and-reinsert or upsert on the natural unique key, isolated per row.
- Every group write wrapped so one (target, group) failure is recorded and the batch continues.

### 3. Dialog UX — `CopyPropertySettingsDialog`

- `ResponsiveModal` / `AdminDialogShell`, 4 steps with a segmented progress header (same pattern as the Marketing "Generate with AI" wizard).
- **Step 1 — Source:** pre-filled from the card ⋯ menu; a `Select` of the org's ACTIVE + INACTIVE properties from the header.
- **Step 2 — What to copy:** grouped checkbox tree (Listing content · Pricing · Guest form · Notifications & bot · Templates · Public pages · Marketing · AI & voice · Team roles · Recurring finance · Recurring maintenance). Parent = select all leaves; each leaf shows its plan badge. `contact`, per-module Telegram credentials, and email recipient addresses default **off**.
- **Step 3 — Targets:** checkbox list of every **other** property in the org (name + tower/unit + plan pill + status), "Select all", search. Rows the actor can't edit are disabled with a reason tooltip.
- **Step 4 — Review:** calls `copy-property-settings` with `dryRun: true`; renders per target — `N groups apply`, `M skipped (plan)`, `K skipped (permission)`, `already customized: …`. Primary **Copy settings** runs it for real. Success toast (`Settings copied to N properties`); partial failures list target/group + server reason.
- Mobile: full-screen sheet, one step per screen, 44px targets.

### 4. Edge function — `copy-property-settings`

- `serveAuthenticated('copy-property-settings', handler)`, POST only; registered in `supabase/config.toml` with the same `verify_jwt` policy as other authenticated functions.
- Body: `{ sourcePropertyId, targetPropertyIds: string[], groups: CloneGroupId[], options: { copyContact, copyEmailRecipients, copyTelegramCredentials }, dryRun?: boolean }`.
- `verifyPropertyAccess(req, sourcePropertyId, 'settings:view')`; load source `organization_id`; reject any target whose `organization_id` differs.
- Per target: `ensurePropertySettings(targetId)`; then per selected group — for each `editLeaves` leaf `verifyPropertyAccess(req, targetId, leaf)` (catch → `skipped: { group, reason: 'permission' }`); `resolvePropertyEntitlements(targetId)` and check `planFeature` (→ `skipped: { group, reason: 'plan' }`).
- `read` once per group from the source; then `sanitize` + `write` per target inside a per-(target, group) try/catch. `dryRun` runs `read` + `sanitize` + `hasNonDefault` only, no `write`.
- Asset groups call `propertyAssetClone` before `write`.
- On a real run: insert one `property_settings_copy_log` row (`results` JSONB per target/group), fire `createNotification` per affected target + one dedup email to the org owner and target teams (reuse the post-payment-save notice sender pattern).
- Response: `{ dryRun, results: [{ targetPropertyId, applied: CloneGroupId[], skipped: [{ group, reason }], failed: [{ group, error }], alreadyCustomized: CloneGroupId[] }], logId? }`.

### 5. Asset cloning — `_shared/propertyAssetClone.ts`

- Input: source object URLs/paths + target `property_id` + bucket id.
- Downloads each object with the service client, re-uploads to the target's path using `_shared/uploadService.ts` conventions, returns `Map<oldUrl, newUrl>` for the group's `sanitize` to rewrite.
- Buckets: `property-media` (gallery), `app-settings-assets` (GAF signature), template section-image bucket (confirm exact id — `templates` vs `property-templates` — in Phase 2), `marketing` (design assets).
- Per-object failures reported, never fatal; never deletes source objects.

### 6. Guardrails

- **Idempotent replace** per group — safe to re-run; a second identical copy is a no-op.
- **Batch isolation** — one (target, group) failure never affects another.
- **Plan-aware** — a group the target's plan disallows is skipped + reported, never forced.
- **No privilege escalation** — every write passes the same leaf + plan gate a manual edit would.
- **Cache coherence** — `invalidateAppSettingsCache(target)` + any other shared-reader cache after each write.
- **Audit + notify** — `property_settings_copy_log` + in-app + email.
- **Registry = source of truth** — mirrored in `docs/PROJECT.md`; a new settings surface later means a new registry entry (add to the `documentation-maintenance` checklist).
