# Agentic AI: dashboard assistant + guest receptionist

## Context

Today the host **dashboard assistant** and the guest **AI receptionist** (web chat, Meta inbox auto-reply, host "Suggest") mostly react: they answer one thing, take one action, and stop. The goal is agentic behavior like Claude Code or ChatGPT. The AI should:

- break a request into every sub-task in it
- plan the steps
- chain several tools, with independent reads running in parallel
- recover from tool errors
- check that every part of the request was handled before replying

All existing guardrails stay: RBAC per tool, risk tiers, grounding and safety guards, plan gates, AI limits and audit.

**Decisions taken (user answers, 2026-11-01):**

- **Multi-write approval:** one **plan card**. The agent proposes every write step, the host ticks or unticks steps and approves once, then the agent runs them in order and reports results. Low-risk Tier-1 steps can still run automatically.
- **Guest scope:** live read tools, a real handoff to the host, **and safe guest writes**:
  - booking inquiry / hold request
  - early check-in / late check-out request
  - maintenance report

  Anything binding still needs host approval.

- **Model:** stay on **Gemini**. Turn on a thinking budget for planning, and route complex turns to a stronger tier at turn start.

**Phase 2 item 3 (dynamic tools), dashboard assistant, done (2026-11-01).** New `_shared/ai/agent/toolRegistry.ts`: a `request_tools(modules[])` meta-tool the model can call mid-turn to widen its own tool set when the deterministic router under-matched (e.g. a question's second half needs a module the first half didn't signal). `widenToolsForModules` adds every declaration for the named modules to the turn's mutable `currentTools`, deduped, and reports back which modules were added vs. an already-complete module vs. an unrecognized module name (never silently dropped). `currentTools`/`currentModules` are `let`, not `const`, so the next round's `generateWithTools` call picks up the widened set — still only _between_ rounds, never mid-round, same thought-signature constraint as model policy above. The call itself never runs anything and is excluded from the activity timeline/task plan (same `rejected: true` path as a rejected duplicate).

Did **not** build a separate per-tool metadata catalog (module/tier/read-write/plan-feature/permission-key) as the plan's target-architecture table describes — that already exists, just spread across `ASSISTANT_TOOL_MODULES` (module), `READ_TOOL_NAMES`/`WRITE_TOOL_NAMES` (read vs write), and each tool's own permission/entitlement check inside its handler. Building a second, parallel registry would drift from those on day one; `toolRegistry.ts` reuses them instead.

**This is explicitly not a security boundary**, and the plan's verification line ("a plan-gated org can't reach gated tools through `request_tools`") holds for a reason worth stating plainly: every tool already re-checks its own permission and plan entitlement _at call time_, inside its own handler, regardless of whether the router sent it on round 1 or `request_tools` added it on round 5. Widening the offered list changes only what the model can _try_, never what a call _succeeds_ at. Said another way: a caller who can already reach a gated tool by name could always have asked for it; `request_tools` doesn't add a reachable surface, it adds a discoverable one.

### Dashboard assistant

- **Tools and routing:** about 100 or more tools across sibling `_shared/dashboardAssistant*Tools.ts` files. A regex tool router (`_shared/dashboardAssistantToolRouter.ts`) picks them.

What blocks agentic behavior:

1. **One Tier-2 proposal per turn.** `proposedAction` is a single variable, and a proposal ends the loop (idx:828, 859). Other proposals in the same round are silently lost. After confirm, nothing goes back to the model.
2. **Tier-1 writes only preview.** The model never sees the real outcome, and commits happen after the answer is built.
3. **The tool set is fixed per turn by regex.** If round 1 shows a need for another module, the model can't reach it. Also, `recentToolNames` is always empty (idx:650-656), because history holds only text snippets. That is a bug.
4. **No planning or reflection.** `thinkingBudget: 0`, max output 2048 tokens, Flash only, and no final check that every sub-request was covered.
5. **Tools run one after another** within a round.
6. **Bulk escalation is checked per round** (idx:745), so spreading writes across rounds gets around it. That is a guardrail gap.
7. **History is text only:** about 320-character snippets plus an 1,800-character summary. IDs and results from earlier turns are lost.
8. **Running out of rounds or budget** produces a fixed summary plus a "Continue" chip. There is no saved plan to resume.
9. **No turn-level time limit.** 8 rounds × 45s can go past the edge function's wall-clock limit.
10. **Hard-coded intent patches:** the mark-done regex (idx:883-904), the Meta refusal, and auto-open pages.
11. **Evals only score the first tool chosen** (`supabase/functions/tests/evals/runLiveEvals.ts`).

## Target architecture

### A shared agent runtime for every chat surface

New folder `supabase/functions/_shared/ai/agent/`. The dashboard and guest surfaces become thin adapters: a tool catalog, a context builder, a guard and an output renderer.

| Module               | Responsibility                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agentLoop.ts`       | Generic round loop built on `generateWithTools`/`generateWithToolsStream`. Runs reads in parallel and writes in order. Detects loops (the same call with the same arguments twice). Has a stop policy and emits events through a callback. This is the existing dashboard loop pulled out of `index.ts` with no behavior change at first.                                                                   |
| `turnBudget.ts`      | Per-turn limits: rounds, tool calls, writes, credits and **wall-clock deadline** (default 110s, below the edge limit). | `turnLedger.ts`      | **Turn-level** record of reads and writes, untrusted-data exposure and proposed steps. It replaces the per-round `isBulk` and stays with a plan across confirm and resume.                                                                                                                                                                                                                                  |
| `taskPlan.ts`        | Internal `plan_task` tool. The model writes a list of sub-goals (id, goal, status, toolHints) before acting and updates it as it goes. | `toolRegistry.ts`    | Catalog with metadata per tool: module, tier, read/write, parallel-safe, plan feature, permission key. The router seeds round 1, and widening is limited to modules allowed for the caller's permissions and plan.                                                                                       |

Entries go in `aiModelRouter.ts` (`dashboard_assistant_complex`, `guest_receptionist_agent`). |

### Phase 2: Reasoning, planning and multi-intent (dashboard)

1. **Model policy:** add `modelPolicy.ts` with a thinking budget (e.g. 1024–4096) and raise max output tokens for complex turns. Add the two new feature keys to `aiModelRouter.ts`, with env overrides as today.
2. **Plan step:** an internal `plan_task` tool. The prompt rule is to plan first when the message has 2 or more asks or any write. The plan is streamed and saved on the message.
3. **Dynamic tools:** a `request_tools` meta-tool in `toolRegistry.ts`, plus cross-module tool hints in tool results (e.g. `inbox` results suggest `pricing`).
4. **Parallel reads:** `Promise.all` for tier-0, parallel-safe calls within a round. Writes stay in order.
5. **Error recovery:** classify tool errors (`_shared/assistantToolFailureReason.ts` already exists): retryable, fix the arguments, or permission/plan denied. Give the model a structured hint. Cap 1 retry per call.
6. **Clarify instead of guessing:** formalize a `clarify` block. Use it when a required argument is ambiguous (which booking? which dates?) and can't be resolved by a read. Prefer reading to asking.
7. **Completion check:** add `completionCheck.ts` and the matching response rule: every sub-request is answered or listed as not done, with a reason.
8. **Prompt rewrite:** restructure `_shared/ai/prompts/dashboardAssistant.ts` around an agent operating loop (understand, plan, gather, act, verify, report) and bump the prompt version.

### Phase 3: Plan-card approval for multi-step writes (dashboard)

1. **Migration** (new file): `ai_dashboard_assistant_action_plans` table with:
   - `id, conversation_id, message_id, org_id, property_id/parking_id, user_id`
   - `status` (`proposed | approved | running | completed | partially_failed | cancelled | expired`)
   - `ledger` jsonb, `expires_at`

   Add `plan_id`, `step_index`, `depends_on int[]`, `selected bool` and `result` jsonb to `ai_dashboard_assistant_pending_actions`. Add RLS matching the existing assistant tables. Update the expire cron so it covers plans too.

2. **Loop change:** a Tier-2 proposal no longer ends the loop. The agent collects every proposed step into the turn ledger and finishes when it has a full plan, or reaches the step cap (e.g. 10). Tier-1 steps in a plan with any Tier-2 step join the plan card (shown as low risk, pre-ticked). Tier-1 steps on their own keep the current deferred auto-commit.
3. **Dependent steps:** a step can refer to an earlier step's output with a placeholder (e.g. `{{step1.bookingId}}`), resolved at run time. Each step is re-checked right before it runs: `assertActionSafeToExecute`, RBAC, plan gate and the write cap.
4. **Confirm endpoint:** `dashboard-assistant-confirm` accepts `{ planId, selectedStepIds }`.
   - Claim the plan atomically.
   - Run the steps in order.
   - Stop at the first failure, skip the steps that depend on it, and keep the independent ones.
   - Stream progress events.
   - Then run a **continuation turn**: step results go back to the agent loop, which writes the final summary and any follow-up reads.
   - Keep the single-action confirm as plan-of-one for backward compatibility.
5. **UI:**
   - A new `ActionPlanBlock` in `ui/src/features/dashboard/ai-assistant/components/blocks/`. It shows numbered steps with a checkbox, a risk badge, a diff/preview line and dependency hints, plus per-step live status while the plan runs.
   - Buttons: Approve selected, Cancel.
   - Extend `assistantStream.ts` and `useAiAssistantChat.ts#resolveAction` for plan resolution.
   - On mobile, the plan opens as a bottom sheet (mobile-responsive skill). Copy goes through `human-copy`.
6. **Unblocks** `ai-assistant-bulk-pricing-chat.md` (diff preview per step) and `ai-assistant-parking-broadcast-chat.md`. Update both plans to depend on this one.

### Phase 4: Working memory and resumable turns

1. **Per-message `entity_refs` jsonb** (migration): compact references to bookings, threads, dates, items and amounts the turn touched, plus short tool-result digests. `dashboardAssistantConversationContext.ts` replays these as structured "Known from earlier in this chat" facts, so the agent doesn't re-ask or re-search. This is session-scoped only, keeping the removal of standing memory (§9.6).
2. **Resumable plans:** when rounds, budget or the deadline run out, save the open `taskPlan` on the message. The "Continue" chip resumes from that state instead of starting over.

### Phase 5: Agentic guest receptionist (web chat + Meta inbox + Suggest)

1. **Wire the tool loop.** Replace `suggestInboxReply`'s single call with the shared `agentLoop`, using a guest adapter built from `guestReceptionistTools.ts`:
   - 4 rounds, parallel reads, full structured tool results (not just `spokenText`), several cards
   - quota checked properly
   - pass in `guest_user_id`, so `get_my_stay` works for authenticated guests

   Use one path for web auto-reply (`webInboxAutoReply.ts`), Meta (`metaInboxAutoReply.ts`, which keeps the 24h window) and host Suggest (`social-inbox-ai-suggest`, staff actor, no guest writes).

2. **Answer every question:**
   - The input becomes all guest messages since the last outbound reply, not only the latest.
   - Rewrite the prompt (`ai/prompts/inboxReply.ts`) so it lists the guest's questions, answers each one and stays short.
   - Merge it with the near-identical `ai/prompts/guestReceptionist.ts`.
3. **Real handoff:** `handoff_to_host` sets a `needs_host` flag and reason on `social_conversations` (migration), sends a host notification and Telegram ping through the existing services, writes an `activity_log` entry, and stops auto-replies on that thread until the host replies. The UI gets a "Needs you" badge in the inbox thread list.
4. **Safe guest writes** go through a new guest risk tier. The AI collects the details, the guest confirms in chat with an inline card, then a **request** is created. Nothing binding happens until the host approves.
   - `request_booking_inquiry`: dates and guest count, checked against `availabilityService`. It creates an inquiry/hold-request record using the existing inquiry flow if there is one (check `inquiry` tables at implementation time), or a new `guest_requests` table.
   - `request_early_checkin_late_checkout`: only for the guest's own verified booking.
   - `report_maintenance_issue`: verified active stay only. Creates a maintenance item through `maintenanceService.ts` with source = guest_ai, and the host gets notified.

   Guardrails for these writes:
   - authenticated guest only, scoped to their own booking
   - per-guest rate limits (e.g. 3 requests a day)
   - no write when the thread is flagged by the guard
   - an `activity_log` event for each
   - plan-gated behind a new entitlement key (`aiReceptionistActions`)

5. **Guard upgrade:** `inboxAiSafetyGuard.ts` checks every number and fact in the reply against the structured tool results, not only precomputed facts. That avoids false fallbacks on richer answers. Keep the fallback-to-host behavior.
6. **Voice:**

   - Expose the same handoff and request tools, with spoken confirmation before any write.
   - Add a post-call guard pass on the transcript and summary.

### Phase 6: Guardrails for more autonomy (applies to Phases 2–5)

- **Turn and plan budgets** enforced in `turnBudget.ts`. Limits are super-admin only via `aiLimitResolver.ts`: new keys for max rounds, max plan steps, a guest request cap and a per-turn credit ceiling. Hosts only get toggles (per memory note _AI limits are super-admin only_).
- **Untrusted-data exposure stays sticky** across the whole plan. Once guest text has been read, every write in that plan is Tier-2 and shown on the card, and `external_send` is always Tier-2.
- **`request_tools` can never grant** a module the caller lacks a permission or plan for. Each tool still re-checks the JWT.
- **Loop detection and caps:** the same call with the same arguments twice ends the round, and each tool call has a timeout.
- **Credits:** count credits per turn and show them in `latency_breakdown`. Check quota before each round (as today), and stop cleanly with a partial answer when credits run out. Coordinate with the atomic reserve/settle in the paid-provider plan, without duplicating it.
- **Kill switches:** global and per-org flags for `agentic_mode`, `plan_approval` and `guest_actions` via feature availability, so it can roll out gradually.
