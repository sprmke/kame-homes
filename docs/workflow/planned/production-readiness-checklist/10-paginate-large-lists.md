# 10 — Paginate large lists

## Implementation status (2026-09-17)

**Phase 10.2 (fix the two known unbounded queries): done, scoped precisely — and independently code-reviewed, with two real bugs found and fixed.**

- **New migration** `20261316121500_guest_submissions_stay_date_sort_columns.sql` adds `check_in_date_sql`/`check_out_date_sql` — generated, indexed `date` columns on `guest_submissions`, computed from the existing `MM-DD-YYYY`/`YYYY-MM-DD` TEXT columns via pure immutable string rearrangement (`make_date()` from extracted parts — `to_date()`/`text::date` are **not** IMMUTABLE in Postgres and cannot be used in a `GENERATED` expression; this took two failed local-migration attempts to discover). A row whose text matches neither format gets `NULL` rather than blocking the write, mirroring the TS `checkInDateToIso` helper's own fail-safe behavior.
  - **Review finding, fixed:** the first version validated digit-grouping (the regex) but not calendar validity — `make_date(2024, 13, 45)` and `make_date(2023, 2, 29)` both **throw** rather than returning NULL, confirmed empirically against local Postgres. A garbage-but-format-matching row (e.g. `"13-45-2024"`) would have failed every future insert/update, contradicting the migration's own stated goal. Fixed by range-checking month (1-12) and day (1 through that month's actual day count, leap-year aware via `extract(day from (make_date(y,m,1) + interval '1 month' - interval '1 day'))`) in the `CASE` guard before calling `make_date`. Re-verified: `"13-45-2024"` → NULL, `"02-29-2024"` (valid leap day) → `2024-02-29`, `"02-29-2023"` (invalid, not a leap year) → NULL, no crashes.
  - **Known, documented divergence (not fixed — out of scope):** for a malformed date row, the SQL fast path treats it as NULL (sorts to a fixed end); the JS fallback path's `checkInDateToIso` returns the raw string unchanged (sorts lexically, essentially arbitrarily, among real dates). The same row can appear in a different position depending on which path serves the request. Fixing this means changing `checkInDateToIso`'s fallback behavior, which is also relied on by `analyticsService.ts`, `dashboardService.ts`, and `importCommitStatus.ts` — a bigger change than this pagination fix, and out of scope. Documented in code at both call sites. Zero malformed rows exist in local seed data; this only matters for legacy production rows, if any exist.
- **`listBookings`** (`_shared/databaseService.ts`): added a SQL fast path used when the request is a **single-property or single-parking scope** (not an org-wide union, and not a parking scope with pending pre-claim broadcasts unioned in — both of those need the existing in-memory dedup, since a union of heterogeneous queries can't be correctly paginated by applying `.range()` to each side independently), the sort is `check_in_date`/`created_at` (not the composite `status_priority` default, which needs a status-priority `CASE` expression not built in this pass), and there's no `from`/`to` range filter. That combination now runs one SQL query with `.order()` + `.range()` + `count: 'exact'`, instead of fetching every matching row and sorting/paginating in memory. The `status_priority:asc` default sort and org-wide scope still use the original fetch-all path — narrowing those further needs either a SQL status-priority expression or restructuring the multi-request union, both larger changes than this pass's scope.
  - **Review finding, fixed:** `total: count ?? paged.length` silently under-reported the true row count if PostgREST ever returned `count: null` on a successful response (e.g. 500 matching rows with `limit=31` would report `total: 31`, hiding 469 rows from the admin UI's pagination). Changed to throw if `count` comes back `null` — fail loud instead of silently wrong.
  - **Review finding, fixed (maintainability):** the fast path had re-implemented the same five filter blocks (`bookingKind`, `searchOr`, `status`, `hasPets`, `needParking`) the fallback path already builds, in a second copy in the same function — a future filter change applied to only one copy would silently make the two paths disagree on which rows match. Extracted into one shared `applyBookingsListFilters` helper used by both branches. Also consolidated the sort-column allowlist check (previously four separate string-literal comparisons, then a second identical destructure two lines later for the actual `.order()` call) into one `sort.split(':')` used by both the eligibility guard and the query.
  - **Review finding, fixed (fragility):** the fast-path guard's parking-broadcast check depended on a variable (`pendingBookingIds`) hoisted out of its originating `if (parkingId)` block purely so a later guard could read it — a refactor of that block could silently leave it stale. Renamed to an explicit `hasPendingParkingBroadcasts` boolean with a comment at both the write and read site making the cross-scope dependency visible.
- **`fetchAllBookingsForFinance`**: now pushes the `from`/`to` period range into SQL via the same generated columns, when `basis` is `check_in`/`check_out` (the common case). `basis: 'completed'` still fetches the full status-filtered set, since which timestamp column applies (`settled_at` vs `status_updated_at`) depends on per-row fallback logic, not a single column. The in-memory `filterBookings` pass still runs afterward as a redundant, harmless safety net — the aggregation math itself (`summarizeStays`, `computeBookingFinancials`) was **not** touched or pushed to SQL: reimplementing a financial calculation in SQL is a materially bigger, higher-stakes change than this doc's own Phase 10.2 guidance ("a separate, cheap aggregate query") anticipated, and financial correctness is not a place to guess.
  - **Known, documented divergence (not fixed, and arguably a correctness improvement):** the SQL prefilter now excludes malformed-date rows from a period-bounded report entirely (`NULL >= from` is always false in Postgres). The old all-JS path instead compared the malformed row's raw string lexically against `from`/`to` — an essentially undefined result, not a meaningful "sometimes correctly included" behavior. The new behavior is more defensible, but it is a real change: a finance report's totals can shift for any property with a pre-existing malformed date row. Documented in code.
- **Verified locally against real data, twice** — once after the initial implementation, once again after the code-review fixes above (the shared filter helper and generated-column rewrite touched the exact logic already tested): both passes confirm (a) fast-path pagination has no gaps/repeats across pages, (b) fast-path `total` matches the old fallback path's `total` for the same filters (66 = 66), (c) the `showCompletedBookings` visibility filter produces an identical row count (52 of 66) on both paths, and (d) `fetchAllBookingsForFinance`'s narrow-window count (5 rows) matches an independent raw SQL query exactly.

**Phase 10.6 (CI guard): done — and the guard itself had a confirmed logic bug, found and fixed during code review.**

- **Review finding, fixed:** the original awk state machine reset its tracking window on every new `.select(` match via a `next` statement, which **skipped evaluating a single-line `await x.select(...);` statement entirely** — the single most common unbounded-query shape in this codebase. Reproduced empirically: a genuinely unbounded `const a = await supabase.from('x').select('*');` on its own line produced zero output from the old script. This means the original 150-file allowlist was seeded from a heuristic that was systematically blind to the most common defect shape, while also over-flagging unrelated multi-line chains it could partially see. Rewrote the awk logic to scan every line unconditionally (no `next`-driven skip), re-swept the whole tree, and rebuilt the allowlist from the corrected output (130 files, down from the old 150 — a different, more accurate set, not a subset).
- New `scripts/dev/check-unbounded-select.sh` (same shape as the existing `check-serve-public-rate-limit.sh` — ripgrep + explicit allowlist), wired into `.github/workflows/ci.yml` and `cd-dev.yml`. **Important caveat, stated plainly:** the allowlist reflects the corrected heuristic's honest sweep of the current tree, not a hand-verified defect list — some are real gaps (crons scanning full/platform-wide tables, AI-usage aggregation with no cap); others are false positives the heuristic still can't resolve (e.g. a query builder created once and reused across two branches, so the bound and the `.select(` land in different statements — confirmed for `ai-platform-credit-wallet/index.ts` and `ai-platform-generation-overrides/index.ts`, documented inline in the script). Shrinking the allowlist — verifying each file and either adding a real bound or documenting why it's fine — is the concrete, visible follow-up this guard now makes possible; it was not attempted for all 130 in this pass.
- One incidental fix found during the original audit (pre-review): `super-admin-overview/index.ts` was missing a `.limit(50_000)` on its `ai_platform_usage_daily` query that its sibling `ai_platform_usage_events` query already had — added, matching the existing pattern exactly.

## Goal

No endpoint, query, or UI list can grow unbounded with tenant data. Every list has a server-enforced page size, a stable order, and a cursor that survives concurrent writes.

## Phases

### Phase 10.1 — Audit every list-returning surface

Sweep all 300 edge functions for the unbounded pattern. Flag any query that:

- calls `.select()` without a `.range()` or `.limit()`, **and**
- can return a row count that grows with tenant activity (bookings, line items, messages, notifications, activity, guests, media, logs, AI usage).

Produce a table: function → table → bound present? → worst-case row count at 100 properties × 3 years.

**Static-list exception:** queries over inherently bounded tables (plan catalog, status enums, a single org's property list, team members) do not need pagination. Bound them anyway with a generous `.limit()` as a safety net — an unbounded query over a table that _should_ be small is exactly how one bad row insert takes down a page.

### Phase 10.2 — Fix the two known unbounded queries

**`listBookings`:** push filter + sort + `.range()` into SQL. The blocker is that its sort/filter shape is computed in JS (`bookingsListSort.ts`, `bookingsStatusFilter.ts`). Options, in order of preference:

1. Translate the sort/filter to SQL directly where expressible.
2. If the ordering depends on derived values, add a generated column or an indexed view carrying the sort key.
3. Only as a last resort, keep JS sorting but bound the input window by date range.

**`fetchAllBookingsForFinance`:** push the date-range and status filters into the query and paginate at the DB. Finance totals that must span the whole period should come from a SQL aggregate (`SUM`) rather than by fetching rows to add them up in JS — a separate, cheap query.

**Edge case:** aggregate-over-page vs aggregate-over-set. A summary computed from the current page is wrong. Totals must be a separate aggregate query over the full filtered set, and the UI must not imply the page total is the grand total.

### Phase 10.3 — Standardize the pagination contract

One shape across all list endpoints:

```ts
// request
{ limit: number (default 25, max 100), cursor?: string, sort?: string, filters?: {...} }
// response
{ items: T[], nextCursor: string | null, totalCount?: number }
```

Rules:

- **Server clamps the limit.** A client asking for `limit=100000` gets 100. Never trust the client bound — this is a denial-of-service control, not a convenience (doc 23).
- **Keyset (cursor) over offset** for anything large or realtime-fed. Offset pagination re-scans and skips/duplicates rows when items are inserted between page fetches, which this app does constantly (new bookings, new messages).
- **Deterministic ordering**: every sort must include a unique tiebreaker (`id`) or the cursor is unstable and rows repeat or vanish across pages.
- `totalCount` is **optional and expensive** — a `COUNT(*)` over a large filtered set is its own performance problem. Prefer "load more" over numbered pages; where a count is required, use an approximate count or cache it (doc 12).

### Phase 10.5 — Non-UI consumers

Pagination is not only a UI concern. Audit and bound:

- **Crons** — `contractExpiryCron` loads all orgs and all properties/parkings every tick (already filed). Any cron that scans a whole table must batch and checkpoint.
- **Exports** — finance PDF/CSV export must stream or chunk, not materialize everything in edge-function memory. Edge functions have hard memory and execution-time limits; a large export is the most likely OOM in this codebase.
- **AI context builders** — `dashboardAssistantContext` and inbox AI context must bound how many rows they pull into a prompt. Unbounded here is both a cost and a token-limit failure.
- **Telegram/notification fan-out** — bound and batch recipients.
- **Data sync scripts** — `scripts/data/*` must paginate against the API.

- Add a seed script producing a large tenant (10k bookings, 50k line items, 20k messages) and run the key pages against it — **pagination bugs are invisible at dev data volume.**

## Edge cases

- **Cursor invalidation** — a cursor encoding a sort key breaks when the underlying row is edited or deleted. Encode `(sort_key, id)` and handle a missing anchor by falling back to the nearest position rather than erroring.
- **Filter change must reset the cursor.** Keeping a cursor across a filter change returns nonsense. Include the filter hash in the query key.
- **Realtime + pagination** — a new message arriving while the user is on page 3 must not shift pages. Prepend to the top page only; do not re-fetch the whole list.
- **Deleted rows and page shrink** — the last page can become empty; the UI must fall back to the previous page rather than showing an empty state.
- **Multi-tenant scoping is a security property, not a filter.** Every paginated query must apply its org/property/parking scope in the same query as the pagination. A bound without a scope means page 2 can leak another tenant's rows — the `assertBookingBelongsToProperty` class of bug already found in the launch audit (P1-2). Cross-check doc 22.
- **`.range()` is inclusive** in PostgREST (`range(0, 24)` is 25 rows). Off-by-one here duplicates or drops a row per page.
- **Sorting by a nullable column** — NULL ordering differs between databases and breaks cursors. Always specify `NULLS FIRST/LAST` explicitly.
- **SEO** — infinite scroll on public search hides results from crawlers. This is an SPA with no SSR, so search-engine visibility of listings is already limited; if organic discovery matters, that is a separate architectural decision, not a pagination fix.
